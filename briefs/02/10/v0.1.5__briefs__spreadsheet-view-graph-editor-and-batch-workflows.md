# Issues FS Views: Spreadsheet, Graph Editor, and Batch Workflows

**version** v0.1.5  
**date** 11 Feb 2026  

## Context

These are UI views and interaction patterns for the issue graph database. Even if we don't implement them all now, I want to capture the plans while I'm thinking about them.

---

## View 1: The Spreadsheet View

This comes from direct experience. When I was doing similar work in Jira, we found it was much more usable and powerful to mass-create and mass-edit issues in a spreadsheet-like environment than in Jira itself. Even with an optimised Jira workflow, it was still too slow — too many clicks, too much overhead. Sometimes you just want to type: task, enter, task, enter, task, enter. Or batch-change a bunch of links.

What we did back then was create a Google Sheet that would sync with Jira. You could start with one issue, then load all linked issues into a table. You could see the hierarchy, edit in bulk, and push changes back.

We're going to do this differently now, but the same principle applies.

### Phase 1: Viewer

Load all issues from a starting point into a tabular format. Choose how many levels deep to go (first level linked issues, second level, etc.).

Export formats:
- **Table view** — formatted for viewing on screen
- **Markdown export** — copy/paste friendly
- **CSV export** — for spreadsheet tools
- **JSON export** — for programmatic consumption
- **Graph view** — which we already have

So for any issue, you get five ways to look at the same data: table, markdown, CSV, JSON, graph.

### Phase 2: Editor

Make the table editable. Not full Excel — we need literally 1% of Excel's features. A grid you can edit. Basic sort maybe. That's it.

#### Schema-aware batch creation

This is the key UX: if I'm on a feature issue, and the schema says features can only have user stories as children, then the batch creation UI should already know that. I select "User Story" as the issue type, and then I get rows where I can type titles. Enter, enter, enter. When I save, it batch-creates all the issues and links them to the parent with the correct link type.

The schema constrains the options. The user doesn't have to think about what issue types are valid — the UI only shows what's possible in this context. This nudges users toward maintaining the right graph structure.

#### Text box mode

Even simpler: a text box where each line is a new issue. Select the issue type from a dropdown, then just type:

```
Implement login validation
Add password reset flow
Create session management
Handle token expiration
```

Hit save. Four user stories created, all linked to the parent feature, correct link types applied.

#### The feedback loop

This is critical: after batch creation, **immediately show the graph** of what was just created. The user sees the visual result of what they typed. This creates an organic evolution loop:

1. Brain dump a bunch of ideas/tasks/risks/features — bang, bang, bang
2. See the graph
3. Realise some should be grouped differently
4. Reorganise (move, relink, create intermediate nodes)
5. See the updated graph
6. Repeat

This is how graphs grow organically and stay healthy.

## View 2: The Graph Editor

The graph visualisation we already have needs to become interactive. A D3-based (or similar) environment where you can manipulate the graph directly.

### Core interactions

- **Click on a link** → see the link type, modify the link type
- **Drag an arrow between two nodes** → create a new link (select link type)
- **Click a link and delete it** → remove a connection
- **Click on a node** → view/edit the issue
- **Add a new node** → create a new issue, immediately linked to where you are

### The Reorganisation Workflow

This is the most common and most important workflow. Here's the scenario:

A feature has 20 tasks directly linked to it. That's a graph smell — too many direct children. We need to introduce intermediate nodes (user stories) to group them.

**Step by step:**

1. Start: Feature → 20 tasks (20 edges)
2. Create a new User Story node, linked to the Feature (now 22 nodes, 21 edges)
3. Select 5 tasks and link them to the User Story (now 26 edges — the 5 tasks are linked to BOTH the feature and the user story)
4. Delete the 5 direct links from Feature to those tasks (back to 21 edges)
5. Result: Feature → User Story → 5 tasks, Feature → 15 tasks

The principle: **always add the new edge before deleting the old one**. Never orphan a node. The workflow is always: create the new connection, then remove the old one.

### Drag-and-Drop Move

A shortcut for the above: drag a task node onto a user story node. If the task and the user story share the same parent (the feature), then dragging automatically:

1. Creates a link from the task to the user story
2. Removes the link from the task to the feature

One gesture instead of two clicks. This is the kind of thing that takes 5-7 clicks in Jira. Here it's a drag.

### The No-Orphan Rule

An issue cannot exist without links. It cannot be orphan. The UI should enforce this:

- Prevent deletion of the last link on any node
- If a user tries to unlink the only connection, warn them: "This would orphan the issue. Delete the issue instead, or link it somewhere else first."

This keeps the graph healthy by construction, not by cleanup.

## View 3: Multi-Root Graph View

Two modes of graph visualisation:

### Single root
Start from one node and explore outward. This is the current model — a directional traversal from a root issue.

### Multi-root
Start from multiple selected nodes and visualise the combined graph. Trim, filter, and explore the connections between them. This is more analytical — "show me how these five things relate to each other."

## Summary of Views and Exports

| View | Purpose | Interaction |
|------|---------|-------------|
| Table view | See issues in rows/columns | Read-only, sort, filter |
| Editable table | Batch create/edit issues | Type, enter, save |
| Text box mode | Rapid brain dump of issues | One line = one issue |
| Markdown export | Copy/paste, documentation | Export |
| CSV export | Spreadsheet tools | Export |
| JSON export | Programmatic consumption | Export |
| Graph view (read) | Visualise structure | Navigate, explore |
| Graph editor | Manipulate structure | Drag, link, unlink, reorganise |

## For the Agents

- **Architect**: design the data flow for the editable table. How does batch creation work under the hood? How do we validate against the schema before creating? How does the "save" operation work — atomic batch commit or individual creates?
- **Dev**: start with the read-only table view and exports (markdown, CSV, JSON). That's the quickest win. Then add the text box batch creation mode. The graph editor is the most complex and can come later.
- **Designer**: the spreadsheet view and the text box mode need UX design. How does schema-aware type selection work? Where do the export buttons go? How does the feedback loop (create → see graph → reorganise) flow visually?
- **QA**: test the no-orphan rule exhaustively. Try every possible way to orphan a node — delete links, move nodes, batch delete. The rule should hold in every case. Also test batch creation with large numbers (50+ issues in one go).
- **Cartographer**: the graph editor is your territory. What's the best layout for drag-and-drop reorganisation? How do you show the "before and after" of a reorganisation move? How do multi-root visualisations work?
