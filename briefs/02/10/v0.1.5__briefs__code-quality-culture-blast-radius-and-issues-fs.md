# Code Quality Culture: Reading Code, Blast Radius, and the Feedback Loop

**version** v0.1.5  
**date** 11 Feb 2026  

## The Core Principle

The reason you want well-architected, clean, well-structured code is not just so you can read it. It's so you can **make changes**. You can refactor. You can understand what's going on when you need to implement new features or fix bugs.

The less you understand the code, the less you can refactor it, the worse it becomes over time. We know this from experience. That's why it's critical to have people on the team who understand the code.

## The Familiarity Test

When I look back at code I wrote a year ago, two years ago, it still feels familiar. It still feels like something I understand because it was written in a particular way, with a particular structure. And I can always tell the code that was rushed or accumulated technical debt versus the code that didn't.

This is the bar for all code, including LLM-generated code.

## Culture Is What Happens When Nobody's Looking

I like this definition of culture: **culture is what happens when nobody's looking**. That's what we want for our codebase.

Let's be honest about the past. In most companies:

- Nobody was really reading the larger commits
- A lot of code shipped without proper review
- Commit practices were poor — massive commits with no granularity
- Code coverage and testing capabilities were limited
- It's not like all human-written code was thoroughly reviewed either

So the standard isn't "LLM code must be better than what we had before" — the standard is "every piece of code, regardless of who or what wrote it, must meet the quality bar." Every time you look at code — skim through it, review it, glance at it — it should feel familiar. It should match the standard you want. If it doesn't, the culture is degrading.

## The Opportunity with LLM Code

Even when you start accepting code in larger quantities from LLMs — bigger chunks, more frequent commits — the code should still look like code you would have written. Or code that matches your specs. This isn't about slowing down. It's about maintaining the standard while moving fast.

Every time you bring code in — not just from LLMs, from third-party dependencies too — you should be pushing your standards, verifying the quality, taking a look at it.

## Reading Code: The Underinvested Activity

There's a great point (hat tip to Tudo Girba and the Glamorous Toolkit / Moldable Development ideas): we don't spend enough time creating tools to read code, process code, and understand code. And yet developers spend a huge amount of time doing exactly that — reading code to know where to make changes.

We need more tools, more capabilities, more ways to understand:

- What the code does
- How to refactor it safely
- What the side effects of a change are
- What's connected to what

## Type Safety as a Quality Signal

My architecture is built on Type_Safe. I create types for everything. I don't use raw strings — every string has a specific type, a domain type. This means I can review the specs and the types that have been created and know from that alone whether the code is right.

Runtime type safety takes this further — it's not just documentation, it's enforcement. You can't silently pass the wrong thing.

## Blast Radius Visibility

This is where I want to go next. I want to be able to see the **blast radius** of any change — not just code-wise, but business-wise:

- Did you add a new feature?
- Did you modify an existing behaviour?
- Did you change something on a screen that was supposed to stay the same?
- What user workflows are affected?
- What data paths are affected?

The answer to "what did this code do?" should be explained. Not in a commit message — in a proper, multi-dimensional view: business functionality, user functionality, workflow impact, data impact. This should be part of every pull request.

## The Positive Feedback Loop

Here's why this is powerful: you already know what you WANT to change (it's in the ticket/brief). And you can analyse what the code ACTUALLY changes. So the review becomes a match:

- The ticket says: "change X on this screen"
- The code analysis says: "this commit modifies X on this screen, and also touches Y"
- If they match: great, ship it
- If they don't match: why? Is Y intentional? Is it a side effect? Is it a bug?

This is a blind analysis pattern — one team (or agent) says "I've done this", another team (or agent) says "I detect this change", and you match in the middle. In the past, this kind of cross-verification could never scale. With multiple agents, it can.

## How Issues FS Enables All of This

Everything described above maps directly to capabilities we're building or can build in Issues FS. This isn't a future dream — the architecture supports it.

### Code as issue types

We can represent code structures as issue types in Issues FS. Functions, classes, modules, endpoints — each becomes a node in the graph. Dependencies between them become edges. Now we have a navigable, queryable graph of the codebase that lives alongside the issue graph.

When a commit changes a function, we can trace the edges: what calls this function? What does it affect? What issues are linked to it? The blast radius becomes a graph traversal, not a manual investigation.

### Briefs linked to code changes

The atomic branch workflow (from the earlier brief) already requires that every change links to a task/brief. If the brief says "change X" and the code change touches X, Y, and Z, Issues FS can flag the mismatch. Brief → task → code change → blast radius analysis → all connected in the graph.

### Semantic graphs of code

The semantic text capabilities we're building for documents apply equally to code. Parse the code, create a semantic graph, connect it to the business-level issue graph. Now "what does this code do?" has an answer that spans from the individual function up to the business feature it supports.

### The blind match pattern

With multiple agent roles (dev creates the code, QA analyses the change, architect reviews the blast radius), each agent produces its own graph of what the change does. The conductor matches them. If they agree, merge. If they diverge, investigate. This is the cross-verification feedback loop, powered by the graph.

### Type_Safe integration

Since our code is already built on Type_Safe, the types themselves are a graph. Every domain type, every schema, every Type_Safe class can be represented as a node. Relationships between types become edges. When a type changes, the graph tells you everything downstream that's affected.

### Change history as a graph

Every commit, every change, every refactor is already captured in Git. But with Issues FS, the CONTEXT of those changes is also captured — the brief, the task, the acceptance criteria, the blast radius analysis, the review comments. The code change is one node; all the reasoning around it is the connected graph. This is the "git commits tell you WHAT, the graph tells you WHY" principle from the transaction store brief.

### Pull request enrichment

Instead of a PR with a diff and a description, a PR becomes a graph: the code changes (nodes), the blast radius (edges to affected components), the business impact (edges to features and user stories), the test coverage (edges to test issues), the brief it implements (edge to the original task). The reviewer doesn't read a diff — they navigate a graph.

### Cultural enforcement at scale

The quality bar becomes verifiable. Are the types correct? Does the blast radius match the brief? Are the right tests linked? Is the change documented in the graph? These aren't subjective questions anymore — they're graph queries. Culture isn't just "what happens when nobody's looking" — it's "what the graph verifies whether anyone looks or not."

## For the Agents

- **Architect**: start designing the code-as-graph model. What are the node types for code structures (function, class, module, endpoint)? How do they connect to the issue graph? How does blast radius traversal work?
- **Dev**: as you commit code, think about what metadata would be needed to connect the change to the issue graph. Start with the basics: which issues does this commit address? What files were changed? We'll enrich from there.
- **QA**: the blind match pattern is a testing methodology. Define how you'd independently analyse a code change and produce a "what this does" graph, without seeing the brief first. Then compare.
- **AppSec**: code-as-graph is also a security tool. Attack surface is a graph traversal. Vulnerability blast radius is a graph query. Start thinking about how security analysis maps to this model.
- **Cartographer**: visualise a code change as a blast radius graph. Take a real commit and show: what functions changed, what calls them, what features they support, what tests cover them. Make the blast radius visible.
