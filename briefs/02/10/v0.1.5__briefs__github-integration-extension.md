# Issues FS: GitHub Integration Extension

**version** v0.1.5  
**date** 11 Feb 2026  

## Overview

This is a brief for a new extension project that integrates Issues FS with GitHub — not just issues, but the broader set of data that lives in GitHub and currently has no proper backup, version control, or offline access.

This builds on the GitHub backup use case from the v0.1.3 brief, but goes much further: bidirectional sync, hooks, and ultimately making Issues FS the single source of truth for GitHub data.

---

## The Four Modes

### Mode 1: Pull — Load Data from GitHub

Sync GitHub data into Issues FS artefacts. Not just issues — everything interesting that currently isn't captured anywhere:

- **Issues** — full detail, comments, labels, milestones, assignees, all metadata
- **Projects** — project boards, columns, cards, status
- **Pull requests** — PRs, reviews, review comments, merge status
- **Repo data** — settings, branch protection rules, webhooks, collaborators, topics
- **Actions/workflows** — workflow definitions, run history, status

All of it represented as Issues FS artefacts, all version controlled. Every sync creates a point-in-time snapshot you can diff against the previous one.

### Mode 2: Push — Write Back to GitHub

If you edit a task in your local Issues FS project, push the change back to GitHub issues. This is the write direction of the sync.

Critical here: **conflict detection**. We need hashing and change tracking to:

- Detect if an issue has been modified on both sides since the last sync
- Avoid creating duplicate issues (don't create something that already exists)
- Flag conflicts for manual resolution rather than silently overwriting
- Track what's in sync and what's diverged

Same problem Git solves with commits and merge conflicts, applied to issue data.

### Mode 3: Live Sync — GitHub Hooks

Set up GitHub webhooks so that every time something changes in GitHub (issue created, updated, closed, PR merged, etc.), the change automatically propagates to the Issues FS repo (or whichever repo is assigned as the sync target).

This is the mode that makes Issues FS the **single source of truth** for GitHub data. GitHub issues stops being the master — the Issues FS representation becomes the master, with GitHub as one of the interfaces into it.

### Mode 4: GitHub Action Integration

The easiest adoption path: add a GitHub Action to a repo, and it automatically syncs all the non-commit data to either:

- The same repo (in a designated folder)
- A sidecar repo (dedicated backup/sync target)
- A zip file artefact (per-run snapshot)

Just by adding one action, you get offline backup, version history, and Issues FS graph representation of all your GitHub data. Zero config beyond the action.

## Why This Is Powerful

### GitHub is no longer the single source of truth

Right now, all the non-code data in GitHub — issues, projects, PR discussions, repo config — is locked inside GitHub. You can't version it. You can't diff it. You can't back it up properly. You can't query it in ways GitHub doesn't support. If you delete a repo, it's gone.

With this integration, that data lives in Issues FS, version controlled in Git. GitHub becomes one interface for viewing and editing it, but the data is yours.

### Digital twin of GitHub

You start to have a digital twin of your GitHub infrastructure. All the configuration, all the metadata, all the project management data — captured, versioned, diffable. You can see what changed, when, and recover from any point in time.

### Graph representation

Because it's in Issues FS, all the GitHub data is automatically graph-native. Issues connect to PRs connect to milestones connect to projects connect to repos. You can visualise and query relationships that GitHub's UI can't show you.

## Optimisation Concerns

We don't want to read all of GitHub's data on every sync. Need to think about:

- **Incremental sync** — only fetch what changed since the last sync (use GitHub's `since` parameters, ETags, etc.)
- **Hash-based skip** — if the local hash matches what we last saw from GitHub, skip it
- **Selective sync** — configure which data types to sync (maybe you only care about issues, not PR reviews)
- **Rate limiting** — respect GitHub API limits, queue and batch requests

## Project Structure

This should be its own project/repo following the use-case pattern: `issues-fs__use-case__github-integration` (or similar). Focused, installable, usable standalone.

Dependencies: Issues FS core, GitHub API client (probably PyGithub or direct REST), the CLI for interaction.

## For the Agents

- **Architect**: map out the full data model. What GitHub entities do we capture? How do they map to Issues FS node types and link types? Design the conflict detection and hash-based sync model. This is the critical design work before implementation.
- **Dev**: once the architect has the data model, start with Mode 1 (pull). Get a full sync of issues working first, then expand to other data types. Mode 2 (push) comes after Mode 1 is solid.
- **DevOps**: the GitHub Action (Mode 4) is your territory. Design the action YAML, figure out the auth model (GitHub token permissions needed), and how the sync target gets configured.
- **AppSec**: review the auth model. What permissions does the integration need? What's the minimum scope? How do we handle tokens securely? The webhook mode (Mode 3) introduces an attack surface — incoming payloads need validation.
- **QA**: test sync correctness — pull, modify locally, push back, verify GitHub matches. Test conflict scenarios. Test incremental sync (only changed items). Test the "delete repo, restore from Issues FS backup" workflow.
- **Cartographer**: once we have GitHub data in graph form, visualise it. Show what a repo looks like as an Issues FS graph — issues, PRs, milestones, projects, all connected.
