# Asynchronous Quality Refactoring with Gen AI Agents

**version** v0.1.5  
**date** 11 Feb 2026  

## The Pattern

One of the most powerful capabilities of having agents in the SDLC is NOT adding more code and complexity. It's making the code **better** — easier to understand, better engineered, matching the quality and vision you want. Asynchronous quality refactoring.

## Why Real-Time Copilot Development Breaks Down

The loop of: make a change → wait for the LLM → review immediately → make another change — doesn't work well. Here's why:

The LLM takes 2, 3, 4, 5 seconds. Sometimes more. And in that pause, **you break your mental model**. You were in a flow state — understanding the code, seeing the pattern, knowing what to do next — and then you wait. And the wait is just long enough to lose the thread.

This is why copilot-in-IDE development doesn't feel good. The delay is enough to break your mental model. You're not coding anymore — you're waiting. Then reviewing. Then trying to get back to where you were.

The same problem applies even with faster models. It's not about speed — it's about the interruption to your thinking.

## What Actually Works: Batch and Delegate

What works is coding in a flow — making a number of changes in a row, as fast as you can think — and then **delegating** the refinement to the LLM asynchronously. You come back later and review the results.

This separates two activities that have very different rhythms:

1. **Creative/architectural thinking** — understanding the code, deciding what to change, seeing the patterns. This needs flow state. No interruptions.
2. **Quality refinement** — applying standards, fixing types, adding validations, refactoring to match patterns. This can be delegated. It doesn't need your flow state.

## The Practice: Leaving Notes in Code

The concrete practice that enables this:

### While coding in flow state:
- Leave **TODO comments** in the code
- Leave **notes about what should be connected or improved**
- Leave **issue references** — links to issues in the tracking system that describe the change needed
- Leave **quality markers** — "this function should use Type_Safe", "this needs a domain type", "this validation is incomplete"

### The three-stage distinction:
1. **"I think this should be done"** — a note, an observation, a TODO
2. **"Here's a plan for how it should be done"** — an issue with acceptance criteria, linked in the code
3. **"Here it is being done"** — an agent picks up the issue, implements the change, commits

These separations are important. Not every observation needs to become a task immediately. And not every task needs to be done by you.

### Then, asynchronously:
- The notes and issues get picked up by agents
- Agents create quality refactoring tasks from the TODOs
- Agents execute the tasks — applying Type_Safe patterns, fixing schemas, adding validations
- Agents commit the changes in atomic branches
- You review when you're ready, not when the agent finishes

## Why This Matters: Reading Code IS Development

The thing that's missed in the "AI will write all the code" conversation is that **reading code is development**. Understanding code is how you maintain focus, direction, and vision for what you're building. It's how you keep reducing complexity. It's how you make good decisions about what to change next.

If the code is structured correctly and implemented effectively, it should sometimes be **faster for you to make the change yourself** than to delegate it. That's not a failure of the tooling — that's well-architected code working as designed. The point isn't to delegate everything. It's to figure out, at each moment, what's the most effective thing to do.

The asynchronous model respects this: you make the changes that need your understanding, you leave notes for the changes that don't, and agents handle the rest.

## The Risk of Not Understanding

If you don't understand the code, it's risky to make changes. We had this problem before — with dependencies we didn't understand. But as the previous brief argued, with agentic coding we can actually understand MORE of our code now, because we're bringing functionality in-house instead of hiding it in dependency trees.

The asynchronous quality refactoring pattern extends this: not only are you writing more of the code yourself, you're continuously improving it through delegated refactoring that you review and understand. The code gets better over time, not worse.

## How This Maps to Issues FS

### TODOs and notes as issues

When you leave a TODO or note in the code, it should automatically (or semi-automatically) create an issue in Issues FS. The issue links to the file and line number. The code comment links back to the issue. Bidirectional traceability.

### Quality refactoring as a workstream

Create a standing workstream for quality refactoring tasks. Agents monitor this workstream, pick up tasks, implement changes in atomic branches (per the dev workflow brief), and submit for review. Continuous, asynchronous quality improvement.

### The atomic branch workflow

This connects directly to the atomic branches brief: every quality refactoring task is its own branch, with a detailed explanation of what changed and why. You review when ready. The branch either merges or gets feedback. No flow state interrupted.

### Cost tracking

Every agent-driven refactoring task has a cost (LLM tokens, compute). The cost control brief applies — budget each task, track actuals, flag anomalies. Quality improvement has a measurable cost that can be optimised over time.

### The three-stage pipeline in the graph

The three stages (observation → plan → execution) are three issue states in the graph. You can see at any time: how many observations are pending? How many have plans? How many are in execution? How many are done? The quality pipeline is visible.

## For the Agents

- **Architect**: design the TODO-to-issue pipeline. How does a code comment become an Issues FS issue? What metadata is captured (file, line, context, category)? How do we avoid noise — not every TODO needs to be a task.
- **Dev**: start leaving structured notes in code during development. Use a consistent format that can be parsed: `# TODO(quality): this should use Type_Safe` or `# ISSUE(IFS-123): refactor validation`. We'll automate the extraction later.
- **QA**: the quality refactoring tasks need acceptance criteria too. Define: what does "quality improvement" mean in testable terms? Type safety applied? Schema validated? Tests added? These become the acceptance criteria for every quality task.
- **Conductor**: manage the quality refactoring workstream. Prioritise tasks, assign to agents, track progress. This is a continuous background process, not a one-off cleanup.
- **Librarian**: catalogue the patterns that come up repeatedly in quality notes. If the same TODO pattern appears across many files, that's a systemic issue that needs an architectural response, not individual fixes.
