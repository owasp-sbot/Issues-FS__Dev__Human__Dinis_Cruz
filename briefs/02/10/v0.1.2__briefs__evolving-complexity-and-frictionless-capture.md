# Core Principle: Evolving Complexity and Frictionless Capture

**version** v0.1.2  
**date** 10 Feb 2026  

## The Problem with Every Other System

There are two failure modes in issue tracking:

1. **Too simple** — forces you into an opinionated structure that can't represent reality. GitHub Issues is a good example. It works, but it has limitations — technological, architectural, conceptual, by design vision — that force you into a particular way of working.

2. **Too complex** — has the granularity and flexibility to represent reality, but is so hard to use that people give up. 50-field forms. 20 clicks to create a single issue. 5-10 second delays between each action. Constant page reloads that break your mental model of what you're trying to do.

And this is why people end up in Excel. Because in Excel, you create a table, call a column "issues", type an issue, press enter, type the next one, bang. Five issues in as long as it takes you to type. The medium doesn't fight you.

Trello built an entire business on this insight: sometimes all you need to create a task is a title and a little description. That's it. Every other system required 5 or 20 clicks to do the same thing.

## The Principle: Evolving Complexity

Issues FS must support **growing complexity and growing richness** without requiring it upfront. The complexity should evolve with the user's needs, not be imposed before they've even started.

What this means in practice:

- An issue can be **just a folder with one `issue.json` file**. That's the minimum. Title and maybe a description.
- When you need sub-issues, you add them. The structure expands.
- When you need content folders, references, history, indexes — they appear as needed.
- Configuration only exists when you have configuration changes. No config file means defaults.
- **Every time we see friction** — something that makes it harder to create, navigate, or consume — we should ask: can we simplify this? Can we make this an evolution? Can we parameterise this?

This is design in the real sense — not how it looks, but how it works. Sometimes 5 fields are more user-friendly than 1. Sometimes 20 fields are more user-friendly than 5. And sometimes 20 fields is massive cognitive overkill where you just need 2 things. The system should adapt to where the user is, not where the system wants them to be.

## The Concrete Problem: Forced Folder Structure

We already have this issue. Right now, all sub-issues live inside an `issues` folder. And that makes sense when you have a lot of issues, a lot of projects, root folders like `issues`, `content`, `references`, `history`, `indexes` — the structure helps at scale.

But there are times when what I want is literally: a folder for a project, and inside it, folders for each issue. That's it. No intermediate `issues` folder. No extra nesting. Just the thing.

Navigating today: project → expand → issues folder → expand → release → expand → issues folder → expand → sub-issues. That's a lot of clicks for something that should be obvious.

We need to support both: the full structured layout for complex projects, AND the simple flat layout for cases where the extra nesting is just noise.

## The Solution: Configurable Readers

Move the Issues FS core toward a model where:

- **Readers** (or reader/transformers) know how to interpret different folder structures and file formats
- A **config file** in a folder can override the default conventions — rename `issues` to something else, use a different structure strategy, change how sub-issues are captured
- Config files are **optional** — no config means defaults apply. Parent config can override child config.
- The config folder itself is optional — it only exists if you have configuration changes
- Multiple readers can coexist — different parts of the tree can use different conventions

The key insight: because everything is nodes and edges, the structure on disk is just a serialisation choice. As long as we have a reader for that format, we support it. Call folders whatever you want, structure however you want — the graph is the same.

## Mass Creation: Accept Any Input Format

This connects directly to the universal input idea from the transformations brief. If someone wants to create 50 issues, they should be able to do it in whatever format is fastest for them:

- A **text file** where each line is an issue title
- A **CSV** with columns for title, description, type, whatever
- A **YAML** file with a tree structure defining nodes and edges
- A **markdown file** with a nested list
- A **spreadsheet**
- A **tree-like structure** in any format that connects things

As long as we have a reader/transformer for that format, it works. The reader converts to Issues FS nodes and edges — either persisted to disk or loaded in memory.

This is how you compete with Excel: make it just as fast to create issues, but with all the graph structure and queryability that Excel can't give you.

## The Implementation Direction

Inside the Issues FS core:

1. **Extract the current folder reading logic** into reader classes — the current convention becomes one reader among many
2. **Define the reader/transformer interface** — input: a path or file, output: Issues FS graph (in memory or persisted)
3. **Support a `config.json`** (or similar) per folder that specifies which reader to use and any overrides
4. **Make config cascading** — parent config applies to children unless overridden
5. **Build readers for common formats** — text-per-line, CSV, YAML, markdown lists — alongside the existing folder-based reader
6. **Default to the simplest behaviour** — no config, no extra folders, just works

## For the Agents

- **Architect**: this is a core refactor. Design the reader interface and the config cascade model. How do multiple readers coexist in the same tree? How does auto-detection work (if there's no config, can we infer the format)?
- **Dev**: start by extracting the current folder-reading logic into a reader class. That's step one — make the current behaviour pluggable before adding new readers.
- **QA**: test that the same graph can be represented in multiple on-disk formats and loaded correctly by each reader. Also test the config cascade — parent overrides, missing config defaults, mixed readers in one tree.
- **Librarian**: the config conventions need documentation. What options are available? What are the defaults? How does a user switch from simple to complex structure as their project grows?
- **Cartographer**: visualise the difference between the current forced-nesting navigation and the simplified flat layout. Show the click-count reduction. This is a UX argument that needs to be visible.
