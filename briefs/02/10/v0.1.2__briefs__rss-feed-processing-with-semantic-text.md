# Use Case: RSS Feed Processing with Issues FS Semantic Text

**version** v0.1.2  
**date** 10 Feb 2026  

## The Idea

Use Issues FS — specifically its semantic text and graph capabilities — to process RSS feeds, store them in Git, and create personalised news. This builds on what My Feeds (the AI startup) already does, but layers the Issues FS graph structure on top.

## How It Works Today

My Feeds already grabs RSS feeds and saves them to S3. The new idea is to use Git as the database instead, and use Issues FS to create rich semantic graphs from the feed content.

## The Proposed Flow

1. **Grab an RSS feed** — save the raw feed data as-is (the raw artifact)
2. **Process each entry** — each RSS item gets its own folder, its own mini Issues FS database. Not called "issues" in this context — more like articles, or semantic text entries, or whatever naming makes sense for this domain.
3. **Create the graph** — for each entry, extract and graph:
   - Title → nodes
   - Description → nodes (semantic text decomposition)
   - Links → nodes
   - Author → nodes
   - Every other piece of metadata
4. **Connect across entries** — at a higher level, start connecting dots between entries. Same author, related topics, linked sources, overlapping concepts.
5. **Consume for personalisation** — the graph becomes the input for personalised news delivery, which is what My Feeds does.

## The Key Principle: Service Abstraction

The services that do the transformation should NOT care that they're dealing with RSS. The service interface should be:

- **Input**: here's some text
- **Output**: here's the semantic graph

That's it. The service doesn't know if the text came from an RSS feed, a PDF, an email, or a voice memo. It just processes text into graphs.

You might have a thin context-aware layer on top that knows "this is an RSS entry, so also extract the author, the publication date, the feed source" — but the core text-to-graph service is generic.

This is important because it means the same infrastructure works for any text source, not just RSS.

## Issues FS as the Layer

This is another example of using Issues FS NOT for issues but for structured data. The graph capabilities — nodes, edges, schemas, fractal structure — are exactly what's needed for semantic text processing. We're just calling the nodes "articles" or "semantic text" instead of "issues."

This connects directly to the markdown-as-master-data pattern from the earlier memo: the raw content (RSS entries) is the master data, Issues FS provides the graph representation that makes it navigable, queryable, and connectable.

## Git as Database

Saving to Git instead of S3 means:

- Version history of every feed capture for free
- Diffable — see what changed between feed pulls
- Branchable — experiment with different processing approaches
- The Issues FS graph lives alongside the raw data in the same repo
- Standard tooling (clone, pull, browse) works out of the box

## For the Agents

- **Architect**: design the folder structure for RSS-in-Git. What does an individual feed entry look like on disk? What's the naming convention for the mini database per entry? How does the cross-entry graph work?
- **Dev**: the generic text-to-graph service is the core piece. Design the interface — text in, graph out — and make sure it's completely source-agnostic. The RSS-specific extraction is a thin wrapper on top.
- **Librarian**: this is a cataloguing problem at scale. How do we organise hundreds/thousands of feed entries and their graphs so they remain navigable?
- **Cartographer**: the cross-entry graph (connecting dots between articles) is where the real value is. Think about what connections are most useful for personalisation — topic overlap, author networks, source relationships.
