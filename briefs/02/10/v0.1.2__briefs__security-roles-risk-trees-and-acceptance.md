## New Security Roles

Adding three security roles to the project:

- **CISO** — the chief security officer. Signs off on risks, manages the risk register, drives risk acceptance. In this project the CISO is very technical — coming from the appsec and pen testing world, not a policy-only role. I am the business owner who ultimately underwrites the CISO's decisions.
- **GRC** — governance, risk, and compliance. Owns the risk register, maps vulnerabilities to risks, maintains the risk tree.
- **AppSec** — application security. Code reviews, pen tests, security assessments, threat modelling.

Network security and cloud security tasks go to **DevOps** — makes sense because that's controlled by the CI pipeline and cloud infrastructure. We're not creating 100 roles, so some tasks get delegated to existing roles within their context.

### A note on sub-roles

We need a way to map sub-roles, so that when a task needs a very specific capability (like network security), it gets assigned to the role that covers it (DevOps in this case), with the context that this is a network security task. The task should be tagged to the specific sub-role even if the parent role executes it.

## Vulnerability Philosophy

Here's how I think about vulnerabilities: **vulnerabilities always exist**. Every application has things it's vulnerable to. That's not the question. The question is:

1. Are the developers and the business **aware** of those vulnerabilities? (i.e. are they documented?)
2. Has the risk of those vulnerabilities been **accepted**?

A vulnerability is a fact that has security implications. It's not a crisis — it's a fact. You document it, you assess the risk it creates, and you make a decision about that risk.

### Examples of vulnerabilities we already have

- Data (issues) can be changed/corrupted by anybody with write access to the repo
- Agents running on my machine with my tokens and credentials
- GitHub credentials used to create PRs and give agents access — agents act on MY behalf, not on behalf of themselves
- Lambda functions possibly running with too many IAM privileges
- Claude Code asking for permissions constantly — approve, approve, approve without really paying attention

Every one of these is a real, documented vulnerability. Not theoretical. Backed by evidence.

## The Hyperlinked Risk Tree

This is the model I want to implement, and it maps perfectly to Issues FS.

### How it works

Every risk creates another risk. You follow the **five whys**: why is this important? Why is THAT important? Why is THAT important? Each answer leads to a higher-level risk. Keep going and you end up at the top-level risks of the project.

So the risk register isn't a flat list — it's a tree (a graph, really) where:

- **Vulnerabilities** are at the bottom — facts with security implications, backed by evidence
- **Risks** compound upward — each vulnerability creates a risk, each risk feeds into broader risks
- **Top-level risks** are at the top — the five or so things that actually matter to the project/business

The top-level risk dashboard shows those top risks. Drill down and you see the tree of contributing risks and the vulnerabilities that back them.

I've written extensively about how to do this — I did it in Jira in the past. **Task for me**: share my past writings on security assessments, risk management, and how I implemented this in Jira. Add this as a task/request.

### Risk types

Don't just do cyber security risks. The risk register should cover:

- Cyber security
- Financial
- Reputational
- Operational
- Compliance
- Whatever else is relevant

### Evidence-backed only

Every risk must be backed by evidence. Something that actually exists. No theoretical risks, no sprawling lists of things that might happen. If you can't point to a vulnerability or a fact that causes the risk, it doesn't go in the register. Map risks to real things, then flow them up the tree.

### Pruning

When a vulnerability is eliminated, the connected risk is eliminated or reduced. If I DO have 2FA (which I do), the "no 2FA" vulnerability doesn't exist, so the account compromise risk it fed into is reduced. We can prune the tree — remove branches where the underlying vulnerability no longer exists. Like pruning a real tree — cut dead branches to keep it healthy.

## Time-Bound Risk Acceptance

This is the core principle: **every risk has to be accepted. The only question is, for how long.**

The acceptance duration should match the time we expect a state change — the point at which something will change that affects the risk. Examples:

| Risk | Acceptance Period | Why |
|------|------------------|-----|
| GitHub doesn't allow agent accounts | 6 months | Platform limitation, not changing soon |
| Lambda running with too many IAM privileges | 1 month | We should have tightened this by then |
| Agents using my credentials to create PRs | 1 week | Actively looking for a solution |
| Claude Code permission approval fatigue | 1 month | Need to find a better permissions model |

When the acceptance period expires, the risk comes back for review. Has anything changed? If yes, reassess. If no, re-accept with a new duration. This is something I should be doing regularly — actively managing, reviewing, and re-accepting risks.

The CISO role drives this process. I, as business owner, am the ultimate acceptor of all risks.

## Specific Tasks

### Explore GitLab for agent accounts (DevOps)
GitHub doesn't allow me to create separate accounts for agents — they have this one-account policy. So agents act as me, with my credentials, which is a real security problem. GitLab might support agent accounts where agents can run code changes, create PRs, and run tests under their own identity with scoped permissions. Explore this.

### First security review (AppSec)
Do a security review and analysis of the current environment. This will surface a bunch of vulnerabilities — document each one, link to the risk it creates, and we'll start building the risk tree from real findings.

### Risk register setup (GRC)
Set up the risk register in Issues FS under the GRC role folder. Define the issue types and link types for vulnerabilities, risks, risk acceptance records, and the tree structure. This is Issues FS doing what it was built for — graph-native risk management.

- **CISO**: you're the driver of risk acceptance. Once GRC has the register set up and AppSec has done the first review, you start the acceptance cycle. Every risk gets a duration and a review date.
- **GRC**: own the risk register. Set up the Issues FS structure for it. Define the schemas for vulnerabilities, risks, and acceptance records. Start with the examples I listed above.
- **AppSec**: start the first security review. Code review, environment assessment, document every vulnerability you find as a fact with evidence. Feed into GRC's risk register.
- **DevOps**: you own cloud/network security. Also take the GitLab exploration task — can we get agent accounts with scoped permissions?
- **Cartographer**: the risk tree IS a graph. Visualise it. When the tree starts growing, we need to see the connections between vulnerabilities, risks, and top-level risks clearly.
- **Conductor**: make sure every vulnerability and risk from the first security review gets tracked as Issues FS issues with proper links.
