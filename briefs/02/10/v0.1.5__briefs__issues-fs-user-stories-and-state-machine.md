# Issues FS: User Stories, Personas, and the State Machine Use Case

**version** v0.1.5  
**date** 11 Feb 2026  

## What Issues FS Actually Is

Before the user stories — a clear description of what we're working with.

Issues FS is a file-based issue tracking system powered by graphs. It uses the file system as the database and creates a graph-of-graphs-of-graphs structure, also powered by semantic graphs. It manages issues, development, and essentially creates digital twins of environments.

The fractal nature is the key: every issue gets to define its own centre of gravity if it needs to, but inherits the environment it sits in. So you might have a repo → with projects → with releases → with features → with tasks → assigned to an agent → who is also fixing bugs. All connected. All navigable. All graph-native.

It sits on top of Memory-FS, which abstracts storage so the same issues database can live in memory, on disk (with Git version control), in a zip file, in SQLite, or in cloud storage like S3. Same code, same structure, different backend.

Powered by M-Graph DB for local graph indexes that make it all queryable.

## The Persona Problem

Before listing user stories, we need to acknowledge that "as a user" is too vague. There's an intersection of two dimensions:

### Roles
- Developer
- Product owner / manager
- Architect
- QA
- Agent (AI)
- And all the other roles we've defined (CISO, GRC, librarian, etc.)

### Interface mode
- **Human** — wants visual interfaces, dashboards, navigable structures
- **AI agent** — wants CLI, JSON output, programmatic access, code-level interaction

The same role (e.g. developer) might be a human or an agent, and they need different interfaces to the same data. So user stories should be framed as **"as a [role]"** rather than "as a user", with the understanding that the implementation might differ depending on whether it's a human or agent in that role.

## User Stories

### As a Developer (Human or Agent)

**I need to know exactly what to do.**

- What is the scope of what I'm working on?
- What is the context?
- What's the acceptance criteria?

Issues FS supports this through tasks, actions, objectives, questions — all different issue types that together define the work. Hyperlinked briefs that lead to questions that lead to acceptance criteria. Every piece is an issue type, all connected.

**I need an easy way to create, edit, maintain, and move issues.**

Not 20 clicks. Not a form with 50 fields. Type it, save it, done. The evolving complexity principle applies — start simple, add richness as needed.

### As a Product Owner

**I need to understand what's going on in the project.**

Status across all work. What's done, what's in progress, what's blocked, what's next. The dashboard problem from the earlier brief — but driven by the fact that status should already BE there in the issues database, maintained as work happens.

### As an Architect

**I need my issue data to be version controlled.**

Issues treated like code. Managed with workflows. Stored in a file system. Version controlled with Git. Not locked in a proprietary database I don't have access to. Portable. Exportable. Mine.

### As an Issues Database User

**I need to define the exact graph structure for my environment.**

The schema, the issue types, the link types, the semantic architecture — all customisable per repo, per project, per environment. Issues FS lets you create your own reality for the issues. Not forced into someone else's opinionated structure. Your project, your taxonomy.

### As an Agent Executing a Task

**I need to know exactly what to do, what to document, and what success looks like.**

Same as the developer story, but the emphasis is on completeness of the brief. The agent starts with a blank context — everything it needs must be in the issues. Hyperlinked briefs → questions → acceptance criteria → referenced files. All issue types, all connected.

**I need a powerful way to capture state, decisions, and actions as I work.**

As the agent progresses, it updates the issues database. Decisions get recorded. Actions get logged. State gets captured. The trail is left behind automatically because the work IS the graph.

This connects directly to the file-system-as-transaction-store brief — the issues database becomes the execution log.

### As an Agent Needing a State Machine

**I need a state machine environment to manage my state.**

This is the really interesting one. State IS a graph. An agent's current state — what it's working on, what it's decided, what it's waiting for, what it's completed — is a graph of nodes and edges. Issues FS is exactly that.

So Issues FS becomes the agent's state machine:

- Current state = current issue status across the graph
- State transitions = issue updates, new links, status changes
- State history = the version-controlled trail of all changes
- State query = graph queries against the issues database

And because it runs in memory (via Memory-FS), an agent can spin up its own private state machine in milliseconds, use it during execution, and either persist it or throw it away.

### As Any Role

**I need self-contained, distributable units of work.**

Issues and issue graphs that can be packaged, distributed, logged, captured independently. Send someone an issue (or a subtree of issues) and they have everything they need — context, acceptance criteria, references, history. Because it's just files, you can zip it, email it, commit it, sync it.

## The Mini-Jira Insight

Think about what an in-memory Issues FS instance actually is for an agent: it's a mini Jira. A mini GitHub Issues. But 100% customised — it has the correct structure, the correct issue types, only the exact types needed for this specific task. No noise, no overhead.

It's a great way to guardrail development (the agent can only work within the defined structure) and a great way to understand what was done (the complete trail is in the graph).
