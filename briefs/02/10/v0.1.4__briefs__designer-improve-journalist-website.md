# Designer Brief: Improve the Journalist Website

**version** v0.1.4  
**date** 11 Feb 2026  

## Context

The journalist website is functional but very vanilla. Now that we have a designer on the team, we can do much better. This brief defines the workflow for the designer to drive improvements.

## Key Objective

The end goal is a **solid, detailed brief that the Dev can implement and the QA can test**. The design proposals and mockups aren't decoration — they're the spec. By the time this workflow completes, there should be zero ambiguity about what to build.

## The Workflow

### Pass 1: Research — Designer Interviews the Team

The designer should interview the following roles and collect their thoughts on what could make the website better:

- **Journalist** — they own the content and use the site daily. What's working? What's friction? What do they wish it could do?
- **Architect** — structural ideas. What's possible technically? What constraints exist?
- **Developer** — implementation perspective. What's easy to change? What's hard? Any quick wins?
- **QA** — this is critical because QA is also the user experience lens. What's confusing? What do users struggle with? What breaks?

For each interview, we should have a folder containing:

- The **questions** asked
- The **answers** received
- An **analysis** of the key takeaways

Everything hyperlinked — the journalist should help make sure the data is properly connected and sourced. The journalist can also write up the story once the designer has collected the information. Delegate the write-up, keep the designer focused on design.

### Pass 2: Design Proposals

Based on the research, the designer should:

- Create an **analysis** synthesising all the interviews
- Propose a series of **design changes** — layout, UX, usability improvements
- Create **mockups** — even rough ones are valuable. Explore whether we can do a Figma integration, or use a skill or tool for this. Even AI-generated mockups (via ascii art or similar) would be useful to visualise the proposals.
- Apply actual **design skills** — not just moving boxes around, but thinking about user experience, information hierarchy, visual flow, the things a designer brings that developers typically don't.

### Pass 3: Team Review

Take the design proposals back to the architect, developer, and QA for comments. This is different from Pass 1 — now they're reacting to specific proposals, not brainstorming in the abstract.

Collect those comments, then I review the whole package.

## Deliverables

1. Interview records (questions, answers, analysis) — one per role interviewed
2. Synthesis article (journalist writes, hyperlinked to all sources)
3. Design proposals with mockups
4. Team review comments on the proposals
5. Final recommendation for my review

## Exploration: Figma Integration

Add a task to explore whether we can integrate Figma (or an alternative) into the workflow so the designer can produce proper interactive mockups. Would be really cool to have that capability. Even if not Figma specifically — any tool that lets us go from ideas to visual mockups quickly.

---

## For the Agents

- **Designer**: you're driving this. Start with the interviews (journalist first, then architect, dev, QA). Collect, analyse, then propose.
- **Journalist**: support the designer with the write-ups. Make sure everything is hyperlinked and properly structured in folders. Write the synthesis article once the interviews are done.
- **Architect**: make yourself available for the interview. Be honest about what's structurally possible and what constraints exist.
- **Dev**: same — be available, share quick wins and hard problems.
- **QA**: bring the user experience perspective. What have you observed? What would you change? This is your chance to advocate for the user.
