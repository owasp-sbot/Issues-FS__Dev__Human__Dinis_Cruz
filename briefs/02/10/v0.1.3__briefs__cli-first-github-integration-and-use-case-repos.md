# Issues FS: CLI-First Interaction, GitHub Integration, and Focused Use Cases

**version** v0.1.3  
**date** 10 Feb 2026  

## The Direction

Issues FS is getting mature enough that we need to start capturing very specific use cases — things somebody can start using tomorrow with a couple lines of code. Not theoretical. Not "one day." Useful now.

---

## Use Case 1: CLI-First Interaction

The CLI needs to be the primary interface for both humans and agents. Think Git-style commands, built with something like Typer for a clean command-line experience.

### Why this matters for agents

Imagine: I give an agent an issue ID and say "this is what you need to do." All the agent needs to do is run a CLI command — `issues-fs show <id>` or `issues-fs dump <id>` — and it gets a nicely formatted table, or JSON, or YAML, or markdown, whatever output format works best for that agent.

Then when the agent finishes, it uses the CLI to update its status: `issues-fs update <id> --status done`. No complex library imports, no custom code in the project. Just CLI commands.

### Output formats

We should think about what the best output format is for different consumers:

- **Humans on a terminal** → formatted table
- **Agents** → JSON or markdown (test which agents parse better)
- **Piping to other tools** → JSON or YAML
- **Documentation** → markdown

The CLI should support all of these via a flag: `--format json`, `--format table`, `--format md`, etc.

### The power of CLI-as-API

If all interaction goes through the CLI, then:

- You install `issues-fs-cli` once and it works everywhere
- Any agent, any language, any tool can use it — it's just shell commands
- The commit workflow is simple: agent runs CLI commands, changes happen to files on disk, git commit
- Same commands work locally and (eventually) against a remote server
- We don't need to add Issues FS as a Python dependency to every project — the CLI is the interface

## Use Case 2: GitHub Issues Integration

### Read GitHub issues through Issues FS

If you have GitHub integration enabled, the same CLI that reads local Issues FS databases should also be able to read GitHub issues. Same commands, same output formats, but the source is GitHub instead of local files.

This means you can see GitHub issues in graph format, connect them to local issues, and start building cross-source visibility.

### Ephemeral in-memory analysis

This is where it gets interesting. Say I want to load 5 or 10 issues from GitHub (or another repo, or another source) and do some analysis — graph them, find connections, run queries. But I don't want to persist any of it. I just want a quick look.

We should be able to spin up an in-memory Issues FS instance, load the GitHub issues into it, do the analysis, output the results, and throw it away. The CLI imports the Issues FS library natively, so it already has in-memory support. Just use it.

This is the same pattern as the earlier brief about on-demand in-memory loading — it applies perfectly here.

## Use Case 3: GitHub Issues Backup

This might be the killer adoption driver.

### The problem

Most companies don't back up their GitHub issues. If you delete a repo, you lose all the issues, comments, labels, milestones — everything. Ask any company: "if you lost all your GitHub issues tomorrow, how would you recover?" Most can't answer that.

Even if you don't delete — you might want:

- A point-in-time snapshot (before a big migration, before a release)
- An archive when a project closes
- A due diligence package (for audits, acquisitions, compliance)
- An offline copy you can search and analyse without hitting the GitHub API

### The solution

A simple, focused tool that backs up GitHub issues into an Issues FS structure. Run it, get your backup, done. Version it in Git and you have a full history of your issues over time.

We can do this very easily with what we already have.

### Packaging as a focused repo

This should be its own repo with its own identity: something like `issues-fs__use-case__github-issues-backup`. Very specific. Very focused. Very easy for someone to understand: "this backs up my GitHub issues." That's the pitch. That's the README. That's the whole thing.

And this is the model for adoption: small, focused, immediately useful tools built on Issues FS that each solve one specific problem.

---

## The Broader Pattern: Use Case Repos

Every focused use case should get its own repo. Not buried inside the main Issues FS project, but standalone, with its own name, its own README, its own installation instructions.

The naming convention: `issues-fs__use-case__<specific-thing>`

Each one should be:

- **Immediately useful** — someone can start using it tomorrow
- **Minimal setup** — install, run, done
- **Self-contained** — depends on Issues FS core but doesn't require understanding the whole ecosystem
- **Value-obvious** — the name tells you what it does
- **Eventually monetisable** — easy to add a paid tier once people are using it

This is how you drive adoption. Not "here's a powerful graph engine, figure out what to do with it." Instead: "here's a tool that backs up your GitHub issues. Oh, by the way, it's built on Issues FS, and here's what else you can do."

## For the Agents

- **Architect**: design the CLI command structure. Map out the core commands (show, list, create, update, dump, export) and the output format system. Keep it Git-like in feel — discoverable, composable, minimal.
- **Dev**: the `issues-fs-cli` package already exists on PyPI. Extend it with the commands described here. Prioritise: show/list with format flags first, then update, then GitHub integration.
- **QA**: test the CLI with different output formats. Also test the agent workflow: can an agent be given just CLI commands and successfully read, process, and update issues? Simulate this.
- **Journalist**: the GitHub Issues Backup use case is a great story for the public website. "Can your company survive losing its GitHub issues?" is a compelling hook. Draft the pitch.
- **Conductor**: create the `issues-fs__use-case__github-issues-backup` repo structure. Define what "MVP" looks like for this use case — what's the minimum that's useful?
- **Librarian**: as we create more use-case repos, we need a catalogue. How do they relate to each other? What does each one depend on? Keep this mapped.
