# Cost Control: Visibility, Safety, and Anomaly Detection

**version** v0.1.2  
**date** 10 Feb 2026  

## This Is Not About Budgets

Let me be clear about what I mean by cost control, because in most organisations cost control is a draconian finance exercise — "spend less." And it creates perverse incentives. The teams with the most cost visibility are often the ones who get their budgets cut, because they gave the business a way to say "I want this, I don't want that." Meanwhile teams with no visibility spend hundreds of thousands or millions unchecked.

Classic example: a cloud team with detailed cost breakdowns gets told "cut 10%", but if they'd gone to the business asking for 100k to implement something useful, they'd have been told no. The visible cost gets cut; the invisible cost runs wild.

That's not what I want here.

## What I Actually Want

Cost control as:

1. **Visibility** — know what's being spent, where, by whom, on what. Just mapping the flows gives you insight.
2. **Optimisation** — spend wisely, not less. Know where money is well spent and where it's wasted.
3. **Abuse prevention** — detect when something is consuming more than it should.
4. **Broken system detection** — catch broken automations, recursive loops, runaway processes.
5. **Anomaly detection** — flag when behaviour deviates from expected patterns.

This is especially critical in the agentic world.

## The Agentic Problem

Once you have automation at scale — agents interacting with agents, workflows triggering workflows — it's very easy for things to go out of control. Very easy to create loops. Very easy to create crazy connections that happen behind the scenes with no visibility.

The fundamental problem: you don't see it happening until the bill arrives (or the system crashes, or the tokens run out, or the API rate limits hit).

## The Model: Budget Per Action

Every action that's executed — by a service, by an agent, by an automation — should have a **budget**. Not a hard limit that kills the process, but an expected cost envelope that flags anomalies.

### Token budget example

Say we have a task that uses an LLM. We can estimate in advance:

- Prompt template: ~2,000 tokens
- User data injection: typically ~100 tokens, max ~500 tokens
- Expected response: ~2,000-3,000 tokens
- **Total expected: ~5,000 tokens with a reasonable buffer**

If the actual usage comes in at 50,000 tokens, that means one of three things:

1. There's a **bug** — something is injecting way more data than expected
2. There's a **problem** — the task is more complex than planned
3. We're **under attack** — someone is manipulating inputs to inflate costs

All three are worth knowing about. The budget didn't prevent the spend — it made the anomaly visible.

### Budget as a graph

I like the idea of a **graph of budget** — as you spend credits on one thing, it unlocks credits for the next thing. So the budget isn't a flat allocation, it's a flow:

- Complete task A (budgeted at X) → unlocks budget for task B
- If task A costs 10x more than expected → don't automatically unlock B, flag for review
- If task A costs less than expected → the savings are visible and can be reallocated

This gives you state-flow control alongside cost control. The budget graph IS the execution permission system.

## What We Track

For every action:

- **Expected cost** — what we projected this would cost (tokens, API calls, compute time, whatever the unit is)
- **Actual cost** — what it actually cost
- **Delta** — the difference, flagged if it exceeds a threshold
- **Who/what** — which agent, service, or automation incurred the cost
- **Why** — linked to the task/issue that triggered the action
- **Cumulative** — rolling totals per agent, per workstream, per iteration

All of this lives in the Issues FS graph. Cost data is just another set of nodes and edges connected to the actions they describe.

## The Visibility Payoff

Just having this data — even without enforcing limits — is enormously valuable. You can see:

- Which agents are expensive vs cheap
- Which tasks consistently overshoot their estimates
- Where recursive loops are forming (cost spikes on repeated actions)
- Whether your estimates are improving over time
- Total cost of a workstream, broken down by component

This is the kind of data that makes a CFO very happy, because it's not about saying no — it's about understanding where the money goes and whether it's going to the right places.

## For the Agents

- **Architect**: design the cost tracking schema. What are the node types for budgets, actuals, and deltas? How does the budget graph work — what triggers unlock of downstream budgets? How does this integrate with the action logging we're already building?
- **GRC**: cost control is a governance function. Define the thresholds and escalation rules — at what delta do we flag? Who gets notified? How does this feed into the risk register?
- **Dev**: instrument the current agent workflows with cost tracking. Start with LLM token usage since that's the most variable and easiest to measure. Every LLM call should log expected vs actual tokens.
- **DevOps**: cloud cost tracking (Lambda invocations, S3 operations, etc.) is your territory. How do we capture per-action cloud costs and link them to the Issues FS graph?
- **Conductor**: the budget graph affects how you sequence work. If a task blows its budget, downstream tasks might need to wait for review. Build this into the workflow.
- **QA**: create tests that deliberately trigger anomalous cost patterns (recursive loops, oversized inputs) and verify the detection works.
