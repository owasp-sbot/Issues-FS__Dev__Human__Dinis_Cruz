# Issues FS: File Structure & Path Architecture Refactoring

**version** v0.1.4  
**date** 10 Feb 2026  
**priority** P1 — triggered by a P1 bug around path handling  

## The Problem

We had a P1 bug that exposed a fundamental issue with how we're handling file paths in Issues FS. Looking at the code, it's got string concatenations everywhere for path building. This is bad for two reasons: it's a security vulnerability (path injection), and it's a nightmare to reason about because it doesn't map to the fractal nature of the design.

The whole philosophy of Issues FS is thinking in graphs, thinking in independent and fractal structures. But the source code doesn't materialise that. The code needs to reflect the architecture, or the architecture doesn't actually work.

## What Needs to Change

Every artefact that currently exists as a random file name — issues, schemas, attachments, everything — should have its own construct, its own type, its own schema. Right now we have loose file paths being assembled with string concatenation. What we need is a series of abstraction layer classes that represent each of these things properly.

The key insight is this: **core primitives should not know about each other**. A core primitive should just BE. It should be given content and asked to save. It shouldn't know where it lives, what's next to it, or how the folder structure works.

## The Architecture

Think about it from the bottom up:

- **Folder** and **File** are the only constructs that know anything about paths and storage. They are the only ones that create paths. Everything else delegates to them.
- A **Folder** knows it's connected to a parent folder. That's it. It doesn't know what's inside it semantically — it just knows it contains things.
- The Folder/File layer delegates to **Memory-FS** for actual storage — so it works in memory, on disk, in a zip file, in S3, wherever. The Folder and File classes don't even really know where things are being saved, they just build the path and delegate.
- Everything above that — Issues, Schemas, Attachments, whatever — only knows about its own content and structure. It hands itself to the storage layer and says "save me". It never constructs a path.

This is how you prevent path injection: the things that handle user content never touch paths, and the things that handle paths never interpret user content.

## What This Enables

The current Issues FS structure (folder names, file names, layout) is just ONE of many possible ways to organise things. By putting proper abstractions in place, we can:

- Support multiple different types of issue types (which we already need to do)
- Support multiple different storage locations (which we already need to do)  
- Have different naming schemes, folder structures, organisation patterns — all without changing the core primitives
- Have mini-factories that resolve different layout conventions, so we can handle multiple issue type formats
- Make the whole thing super flexible and configurable
- Actually reflect the fractal nature of the design in the code itself

## The Pattern

```
Content Layer (Issues, Schemas, Attachments, etc.)
  │  — knows about its own content and structure
  │  — has its own Type_Safe schema
  │  — never constructs a path
  │  — hands itself to storage: "save me"
  │
  ▼
Path Layer (Folder, File)
  │  — the ONLY layer that builds paths
  │  — Folder knows its parent, that's it
  │  — File knows its Folder, that's it
  │  — delegates actual I/O downward
  │
  ▼
Storage Layer (Memory-FS)
  │  — doesn't care what's being saved
  │  — handles memory, disk, zip, S3, etc.
```

Nothing in the Content Layer ever sees a raw path. Nothing in the Storage Layer knows what an Issue is. The Path Layer is the bridge, and it's the only place where path construction happens — which means it's the only place we need to secure against injection.

## For the Agents

- **Architect**: design the Folder and File schemas. Define how the path layer interfaces with Memory-FS. Map out how the current file structure gets migrated to this model.
- **Dev**: the P1 bug is the immediate trigger. Fix the path injection surface first, then refactor toward this architecture. Every string concatenation building a path is a target.
- **AppSec**: review the current path construction code and catalogue every injection vector. The new architecture should eliminate them by design, not by sanitisation.
- **QA**: we need tests that verify path injection is impossible through the content layer. Also test that the same content can be stored/loaded across all Memory-FS backends.
- **Cartographer**: map the current file structure patterns against the proposed abstraction. Identify every place where path logic is currently embedded in content-level code.
