# Transformations, Round-Trips, and the Ideas Library

**version** v0.1.2  
**date** 10 Feb 2026  

## The Core Philosophy: No Surprise, Easy Capture

Two principles that should drive everything:

1. **Principle of no surprise** — things should work in ways that make sense. No magic, no hidden behaviour.
2. **Principle of easy capture** — it should be ridiculously easy to get data into the system, in whatever format the user naturally produces it.

---

## Transformations and Projections

For any given data — a file, a dataset, a document, an issue — we should be able to create multiple projections of it. Think of these as different lenses on the same thing.

We'll have two or three highly curated core formats for capturing a graph, but beyond that, we should support projections via:

- **Transformers/loaders** — deterministic conversions between formats
- **LLM-powered conversions** — for cases where the transformation requires understanding, not just parsing

### Suggested Graphs: Preventing the Blank Page

One of the most powerful UX patterns: when a user starts mapping something (a GitHub repo, a document, a new project), we **suggest** the graphs they might want to create.

"We looked at this, and we think you want to create these 5 issues. Here are 10 more we'd recommend."

This is what I'm already doing with semantic graphs — proposing a graph for the content. It makes onboarding and maintenance dramatically more effective because the user isn't starting from scratch. They're reviewing and refining a proposal.

A transformation proposal is itself just another type of issue/node in the graph. It can be visualised, accepted, rejected, modified — all tracked.

This also handles the fact that decisions are often trees, not points. A decision has evidence, a sequence of events, alternatives considered. The suggested graph captures that structure.

## Universal Input: Accept Any Format

I want to make it super easy to capture data. The user should be able to describe nodes and edges in ANY format that makes logical sense:

- `title, description`
- `key: value`
- A pile of descriptions
- A markdown table
- A CSV or spreadsheet
- Triplets (subject, predicate, object)
- RDF/OWL structures
- Any other format that can be logically parsed

We should be able to transform any of these into Issues FS nodes and edges — either persisted to the file system or loaded on demand into memory.

### On-demand in-memory loading

This is important: not everything needs to be saved to disk. You should be able to say "process this file" and get back an Issues FS object in memory — a graph you can visualise, query, apply graph theory to, export to Neo4j, run Spark on, whatever. The source format doesn't matter. You went from structure → in-memory graph. That's the primitive.

The performance concern is a non-issue. You need a ridiculous amount of data before loading into memory causes any real computation delay. And with the fractal nature of Issues FS, you can have an issue that points to a serialisation file that points to another file that points to a zip — as long as you can find it, you can unpack it.

### M-Graph DB as storage

The M-Graph DB could be a nice way to store some of this information — it's another option alongside files-on-disk and in-memory. Nodes and edges, or triplets, whatever representation makes sense for the use case.

The problem with RDF/OWL/triplets has always been that when you look at it raw, it's just an incomprehensible list of nodes and edges. Issues FS solves this because it adds structure — types, schemas, the meta-structure of what things ARE. It's a graph, but it's a graph you can read and navigate.

## Round-Trips: The Critical Capability

This is the most important concept in this memo.

A **round-trip** means: I can go from Format A → Issues FS graph → back to Format A, and the result is faithful to the original.

### Why round-trips are everything

The moment you have round-trip capability, you can:

- **Refactor** — change the structure, reorganise, split, merge
- **Apply changes** — modify data through the graph and write it back
- **Use every tool** — every visualisation, every query, every manipulation technique we build for Issues FS automatically works on the original format
- **Maintain the source** — the user keeps working in their preferred format, we transform, manipulate in the graph, and write back

This is the same pattern I use with HTML: take HTML → create a dictionary → convert to a graph → manipulate the graph → convert back to dictionary → output as HTML. The graph becomes the manipulation layer for the original format.

### Round-trip vs one-way transformers

Not every transformation needs to be round-trip. Some are one-way projections (like generating a summary or a visualisation). But we should explicitly mark which transformers support round-trips, because those are the ones that unlock the full power of graph-based manipulation of source data.

## The Ideas Library

**Task for the librarian.**

Across all these voice memos and documents, there are ideas sprinkled everywhere — half-baked ideas, project concepts, things to do, future developments, stuff that might not get implemented for six months or a year. As I create more of these, we need a way to keep cataloguing them.

### What we need

A section in the library — call it the ideas library, the half-baked section, whatever — that:

- **Captures ideas** as they appear in memos and documents, packaged as individual items
- **Preserves the original** — don't get rid of the source document. Store it with temporal metadata (when it was captured, from what source).
- **Detects overlap** — if I describe something that's already been captured as an idea, the only questions are: am I adding anything new? Or am I introducing a contradiction that needs examination (because maybe my thinking has evolved)?
- **Categorises by timeframe** — some ideas are "next week", some are "six months", some are "maybe someday"
- **Links back to source** — every idea traces back to the memo or document it came from

Issues FS is perfect for this because ideas ARE a graph. They connect to each other, to projects, to decisions, to other ideas. The cataloguing IS the graph-building.

- **Dev**: the universal input parsing is the core task. Start with the most common formats (CSV, markdown table, key-value) and build the transformer that converts to in-memory Issues FS objects. Round-trip support for at least one format first.

- **QA**: round-trip fidelity is a testable property. For every format that claims round-trip support, test: original → graph → back to original. Diff should be minimal/zero.
- **Cartographer**: the suggested-graphs UX needs your input. When we propose "here are the 5 graphs we think you want", how do we visualise that proposal? How does the user accept/reject/modify?
