# Dev Workflow: Atomic Branches, Context-Complete Tasks, and Change Review

**version** v0.1.2  
**date** 10 Feb 2026  

## The Workflow

Every change to the code should be atomic. Dev branch should never be in an unstable state. All development work is small, incremental changes, done one after the other, each in its own branch.

The flow:

1. **Architect** maps out the task — the change request, the fix, whatever it is
2. **Librarian** helps gather the information and references needed
3. The task brief must contain **everything** the dev needs to implement the change. Think about this as the LLM context window: the dev agent will operate in complete isolation with only what's in the brief. Not more, not less. So that means super detailed briefs, super focused execution.
4. **First pass is a planning check** — before the dev starts coding, they answer one question: "do you have everything you need to implement this?" If you loaded a fresh context with only what's in this task — the referenced files, the information provided, even if it's 50k tokens of references — could you do it? If not, what's missing?
5. **All work in branches** — every task gets its own branch
6. **Detailed explanation of every change** — not just what changed, but why, what the blast radius is, what side effects to watch for
7. **I review and approve** — then the branch gets merged
8. **Run all tests** — check for regressions
9. **Repeat**

## The Review UI

I want to design a UI that lets me review changes much more effectively than a standard git diff. I want to understand:

- What changed and why
- The blast radius of the change
- What maps/dependencies were affected (this is why we need the cartographer)
- Visualisation of the change in context, not just line-by-line diffs

We could do projections from the Issues FS data, or load data directly from Git since we have access to the repo. But the goal is a reviewer experience that gives you genuine understanding, not just a wall of green and red lines.

## The Dependency Graph

We need a graph — an acyclic graph — that captures which bug depends on which fix. You might have a branch that depends on another branch, or a fix that can only land after something else is merged. That's a graph, and we should be able to visualise it.

This feeds directly into the conductor's job of sequencing work and into the cartographer's job of mapping what's connected to what.

---

## For the Agents

- **Architect**: you own the task briefs. Every brief must be context-complete — assume the dev starts with a blank slate and only has what you give them.
- **Dev**: before starting any task, explicitly confirm you have everything needed. If something's missing, say so BEFORE writing code. All work in branches, all changes documented.
- **Librarian**: support the architect in assembling references for task briefs. Make sure the right files and context are linked.
- **Cartographer**: two things — help visualise the blast radius of changes during review, and map the dependency graph between branches/fixes.
- **Conductor**: track the branch dependency graph. Sequence the merge order. Make sure nothing gets merged out of order.
