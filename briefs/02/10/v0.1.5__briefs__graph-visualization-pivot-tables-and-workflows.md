# Visualising Large Graphs: Pivot Tables, Navigation, and Workflow State Machines

**version** v0.1.5  
**date** 11 Feb 2026  

## The Problem: Graph Explosion

Once you make it super easy to create nodes and edges, you get an explosion of them. The system promotes granularity — breaking tasks into sub-tasks, ideas into core ideas, concepts into principles. Even just this voice memo, if transformed into a graph, would be massive.

That's a good thing — granularity is the point. But it means we urgently need ways to visualise large graphs without drowning in them.

---

## Technique: Normalised Graphs (No Shared Nodes)

Before we can create the views described below, we need an intermediate step: creating graphs where no node is pointed to by more than one other node. A tree, not a web.

### The problem with shared nodes

In a real graph, many nodes point to the same target. Node A and Node B both point to Node G. This is natural and correct for the data, but it makes certain visualisations impossible because you get tangled webs instead of clean hierarchies.

### The solution: duplicate with unique IDs

For every node, allocate a unique ID — even if the node's VALUE is the same as another node. So if Node G is referenced by both A and B, you create two copies of G, each with a unique ID, one under A and one under B.

M-Graph DB already has a mode that does something similar — you can determine the value via a tag, and if you assign a random value, every node becomes unique.

### What you get

A graph that always looks like a star — growing from a centre with a flow outwards. Every path through the graph is unique. No backlinks, no convergence, just clean expansion.

This normalised form is the foundation for the views below.

## View 1: Pivot Table View

This is for tree-like structures: parent → child → child's child → leaf. Release → features → user stories → tasks.

### How it works

1. Start with the normalised graph (unique paths)
2. Export every unique path as a table row. Each column is a level in the hierarchy. So if you have 100 unique paths, you have 100 rows.
3. Now apply pivot table logic: **merge cells with the same value** at each level.

What you get:

- **Leftmost column**: one big merged cell (the root — everyone shares it)
- **Next column**: a few merged cells (the high-level groupings)
- **Further right**: more cells, less merging, more granularity
- **Rightmost column**: 100 individual cells (one per unique path)

Everything on the left is aggregation. Everything on the right is detail. You read left-to-right from "big picture" to "individual item."

### Why duplicated values matter

At the edges, you'll have cells with repeated values — the same task appearing under multiple user stories, for example. That's correct and intentional. When you're reading from a specific user story's perspective, you WANT to see all the tasks that impact it, even if those tasks also appear elsewhere.

### Implementation

This is easy to create programmatically in Python or JavaScript. We don't need to reinvent pivot tables — we can bring in existing libraries for the interactive version. But the static version (for export, for markdown, for HTML) we build ourselves.

Can also layer on bar charts, aggregation views, and other data viz on top of the pivot table structure.

## View 2: Markdown Navigation Pages

Create flat, navigable views of the issues database as markdown files.

### Why this is powerful

If we save these views as markdown, the issues folders become immediately navigable on GitHub — just normal markdown pages, rendered in the GitHub UI, clickable, browsable. No special tooling required.

This means:

- Static pages generated from the graph
- Renderable anywhere markdown renders (GitHub, VS Code, any viewer)
- Can be generated on demand or committed as part of the repo
- Server-side rendering for the web UI, static pages for offline/GitHub

### What these pages look like

Index pages per project, per issue type, per status. Linked lists of issues with key metadata. Drill-down navigation. All generated from the graph, all just markdown.

## View 3: Workflow State Machine (Evolved Kanban)

Evolve the current status/state flows (which are basically a simple Kanban board) into a complete, mature workflow system.

### What this means

Each workflow is itself a valid graph — nodes are states, edges are transitions. So we model the workflow in the same system we model everything else. States like:

- Brief created → Review → Approved → In progress → QA → PR submitted → Review → Merged

### Why this matters for agentic workflows

Each state transition can be assigned to a specific agent with a specific persona. The brief creation agent hands off to the review agent, who hands off to the dev agent, who hands off to the QA agent. Each one does their part and submits the result. The workflow graph defines who does what, when, and what conditions must be met before the next step.

This makes transitions much more efficient — each agent only needs the context for their step, not the entire history.

## GitHub Actions and Multi-Agent Commit Workflows

### Commit-triggered analysis

We already have Claude Code creating pull requests. The next step: a GitHub Action triggered by that PR that runs analysis — blast radius, test verification, quality checks — and provides information about what the change does.

### Important: Don't lock data in GitHub

Don't use GitHub's PR review features as the data store for this analysis. Instead, have the analysing agent **make another commit to the PR branch** with its findings. That commit is tracked, provides metadata, shows what happened. The data stays in Git, not in GitHub's proprietary review system.

### Multi-agent commit chains

Each agent in the workflow leaves a commit behind — that commit represents what happened at that step. So a PR branch might have:

1. Dev agent: the code changes
2. QA agent: test results and analysis (committed to the same branch)
3. AppSec agent: security review findings (committed to the same branch)
4. Architect: blast radius analysis (committed to the same branch)

Each commit is made to the issue's folder in the repo, creating a traceable chain.

### Safety: Don't merge unvalidated PRs

Some PRs have already broken features because they were merged without QA validation. Rule: a PR should not be merged unless it has the QA agent's validation commit. The validation commit is the gate.

### Future: Per-agent accounts and forks

Ideally, each agent would have its own GitHub account (or org), working on its own fork of the repo. Then the concept of pull request becomes literal — each agent truly submits from its own space. We can simulate this today by reading remotes. The GitLab exploration (from the security brief) is relevant here too.

### Folder-scoped commits

Interesting idea to explore: can we enforce rules that prevent agents from committing outside their designated folder? Each agent only writes to its own area. This is the authorization model for code, applied to the commit workflow.

## For the Agents

- **Cartographer**: the pivot table view and markdown navigation pages are your primary tasks. Start with the pivot table — take the current graph data, normalise it (unique paths), and render the merged-cell view. Prototype in HTML first, then figure out the markdown equivalent.
- **Architect**: the workflow state machine is a graph design task. Define the node types (states) and edge types (transitions) for the agentic workflow. What's the schema? How do we model approval gates, agent assignments, and conditional transitions?
- **Dev**: implement the normalised graph mode in Issues FS core — the "unique ID per node" mode that creates tree-from-graph. Also: the markdown page generator that creates navigable index pages from the graph.
- **DevOps**: the GitHub Action for PR analysis is yours. Design the action that triggers on PR, runs analysis, and commits results back to the branch. Also: explore folder-scoped commit restrictions.
- **QA**: you're the gate in the multi-agent commit workflow. Define what your validation commit contains — what checks must pass before a PR can merge? Make this concrete and automatable.
- **Conductor**: the workflow state machine directly affects how you orchestrate work. Review the proposed states and transitions. Are there missing steps? Bottlenecks? States that should run in parallel?
