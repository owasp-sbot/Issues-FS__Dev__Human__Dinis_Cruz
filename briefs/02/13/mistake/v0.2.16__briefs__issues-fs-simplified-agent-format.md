# Brief: Simplified Agent-Friendly Issue Format for Issues FS

**version** v0.2.16  
**date** 13 Feb 2026  
**from** Human (project lead)  
**to** Issues FS team  
**priority** High — this unblocks widespread agent adoption of Issues FS  

---

## The Problem

Issues FS is powerful. The hyperlinked JSON structure, the typed issues, the typed links, the schemas — it's the right model. But right now, that power comes with a cost: **it's too complex for agents to maintain easily**.

Every issue requires creating a JSON file with the correct structure, in the correct folder, with the correct links. Creating 15 issues means creating 15 files. Maintaining them means editing JSON. Reviewing changes means diffing massive JSON files across dozens of directories.

This creates a friction problem. We want an explosion of issues — tasks, questions, findings, handovers, all captured as issues in the graph. We want roles to communicate in issues. We want agents to instinctively reach for Issues FS the way a developer reaches for git. But the overhead of creating and maintaining properly-structured issues is slowing adoption. Agents can do it, but it's messy, verbose, and error-prone.

The result: Issues FS is underused relative to its value. We need to fix that.

## The Insight

The on-disk representation doesn't have to match the in-memory representation.

Right now, one issue = one JSON file on disk = one node in the graph in memory. The disk format and the memory format are the same structure. But they don't have to be. We can have a **simpler disk format** that Issues FS reads and expands into the full graph representation in memory.

Think of it as compression. The full JSON structure is the uncompressed format — maximum fidelity, maximum flexibility, maximum verbosity. The simple format is the compressed format — less flexibility, but dramatically easier to create, edit, review, and diff.

Both formats coexist. The full JSON structure is still valid, still supported, still the right choice for complex issues with rich metadata. The simple format is for the 80% case where an agent just needs to say "here are 10 tasks, here's their status, here's what they are."

## The Proposal: `.issues` Flat Files

### The Format

A file with a `.issues` extension (or `.issuesfs`) that contains one issue per line in a minimal format:

```
label | status | description
```

That's it. Three fields, pipe-delimited. The minimum viable issue.

Example — a file called `workstream-observability.issues`:

```
enable-cloudfront-logs | todo | Enable CloudFront access logs with IP masking
enable-s3-access-logs | todo | Enable S3 object access logging  
enable-lambda-logs | todo | Enable detailed Lambda execution logging
enable-xray | todo | Enable AWS X-Ray tracing across all services
enable-waf | todo | Enable AWS WAF for CloudFront distribution
create-log-collector | todo | Build the collector pipeline (LETS pattern)
build-dashboards | todo | Create traffic and error dashboards from collected data
cost-analysis | todo | Document cost impact of enabling all logging
devops-brief | in-progress | DevOps brief on all AWS observability settings
dpo-review | blocked | DPO review of logging data protection implications
```

Ten issues. One file. An agent can create this in seconds. A human can read it at a glance. A diff shows exactly what changed.

### Hierarchy via Indentation

Use tab indentation (Python-style) to express parent-child relationships:

```
observability-pipeline | epic | Enable full AWS observability and build analytics
	enable-cloudfront-logs | todo | Enable CloudFront access logs with IP masking
	enable-s3-access-logs | todo | Enable S3 object access logging
	build-dashboards | todo | Create dashboards from collected data
		dashboard-traffic | todo | Real-time traffic dashboard
		dashboard-errors | todo | Error rate and type dashboard
		dashboard-costs | todo | AWS cost tracking dashboard
```

The indentation implies the link type:
- A tab-indented line under a parent is linked with `has-task` (or whatever the default child link type is for that issue type)
- No need to explicitly declare the link — it's inferred from the structure

### Issue Type Inference

The issue type can be inferred from the label or explicitly stated:

```
# Explicit type prefix
[epic] observability-pipeline | todo | Enable full AWS observability
[bug] missing-error-handler | todo | Lambda missing error handler for malformed requests
[question] ip-masking-approach | open | Which CloudFront IP masking method should we use?

# Or inferred from context
# - top-level items in a workstream default to 'task'
# - indented items default to 'sub-task'
# - items with '?' in the description default to 'question'
```

### Link Inference

Beyond parent-child (from indentation), we can support cross-references:

```
enable-cloudfront-logs | todo | Enable CloudFront logs -> dpo-review
```

The `->` syntax creates a link (default type: `depends-on` or `relates-to`). The target is resolved by label within the same database.

### Multiple Files

A single Issues FS database can contain multiple `.issues` files, each representing a workstream, a role's task list, a set of questions, etc.:

```
my-issues-db/
├── workstream-observability.issues
├── workstream-ux-improvements.issues
├── workstream-admin-tokens.issues
├── questions-open.issues
├── bugs-current.issues
└── .issues-fs/          ← (traditional Issues FS structure, auto-generated)
```

Each `.issues` file is loaded and merged into the single in-memory graph. Issues can cross-reference across files.

## The Loading Model

### How It Works

When Issues FS loads a database:

1. **Scan for `.issues` files** in the root and subdirectories
2. **Parse each file** — extract issues, statuses, descriptions, hierarchy, links
3. **Infer issue types** from prefixes, context, or defaults
4. **Infer link types** from indentation and `->` syntax
5. **Merge with any traditional JSON issues** that also exist in the database
6. **Build the full in-memory graph** — the complete, richly-typed, fully-linked Issues FS structure

The in-memory representation is always the full Issues FS model. The `.issues` files are just a simpler way to get data into that model.

### Normalisation (Optional)

An optional command can "normalise" the database — take the in-memory graph and write it out as the traditional JSON file structure:

```bash
issues-fs normalise
```

This converts the compressed `.issues` format into the full JSON structure. Useful for:
- Archiving a database in its canonical form
- Interoperating with tools that expect the JSON structure
- Verifying that the in-memory representation matches expectations

But normalisation is optional. The `.issues` files can remain as the on-disk format indefinitely. The full graph only exists in memory when loaded.

## The Validation Command

This is critical. Because the `.issues` format is freeform, agents need a way to check that what they've written is valid and consistent.

```bash
issues-fs check
```

or

```bash
issues-fs verify
```

This command:

1. Loads all `.issues` files and traditional JSON issues
2. Parses everything into the in-memory graph
3. Reports any problems:
   - Unparseable lines (bad format, missing fields)
   - Unknown issue types (no matching schema)
   - Broken cross-references (links to labels that don't exist)
   - Duplicate labels (same label in multiple files)
   - Schema mismatches (issue type expects fields that aren't present)
4. Reports the resulting database state:
   - Total issues loaded
   - Issues by type
   - Issues by status
   - Links by type
   - Any orphaned issues (no links to anything)

### The Agent Workflow

The briefing to agents becomes:

> Use the simple `.issues` text format to create and maintain your issues. It's easy — one line per issue, label | status | description. Use indentation for hierarchy. Always run `issues-fs check` before committing. If there are errors, fix them. Then review the output to confirm that what Issues FS sees matches what you intended.

This is a tight loop:
1. Agent creates/edits `.issues` file
2. Agent runs `issues-fs check`
3. If errors → fix and re-check
4. If clean → confirm the graph looks right → commit

### Schema Management

The check command should also handle schema evolution:

```bash
issues-fs check-schema
```

This analyses the issues in the database and:
- Identifies issue types and link types in use
- Compares against defined schemas
- For known types (bug, task, epic, question, etc.) — validates against the predefined schema
- For new/unknown types — proposes a schema based on the data observed
- Suggests schema changes if the data has evolved beyond the current schema

Most of this can be done programmatically. If an agent creates an issue with type `security-finding`, and no schema exists for that type, the system can propose a default schema (label, status, description, plus the link types observed). The agent (or a human) approves the schema, and future issues of that type are validated against it.

Predefined schemas for common types should ship with Issues FS:
- `task` / `sub-task` — label, status (todo/in-progress/done/blocked), description
- `bug` — label, status, description, severity
- `epic` — label, status, description
- `question` — label, status (open/answered/deferred), description
- `finding` — label, status, description, severity
- `decision` — label, status (proposed/accepted/rejected), description

If a type isn't predefined, default to the minimum: label, status, description. The schema grows as needed.

## Why This Matters

### Agent Adoption

The barrier to using Issues FS drops dramatically. Creating 10 issues goes from "create 10 JSON files in the correct folder structure with correct link references" to "write 10 lines in a text file." Agents will use it more because it's easier. More usage = more data in the graph = more value from the graph.

### Review and Diff

This is a huge win for the human reviewing agent work. Currently, reviewing Issues FS changes means reading diffs across many JSON files. With `.issues` files, the diff is:

```diff
- enable-cloudfront-logs | todo | Enable CloudFront access logs with IP masking
+ enable-cloudfront-logs | done | Enable CloudFront access logs with IP masking
```

One line changed. Instantly readable. The conductor can include a summary of Issues FS changes in each commit — before and after — and the human can see exactly what moved.

### Communication in Issues

We want roles to communicate via issues — a question from the architect becomes an issue that the dev answers, which links to the task it unblocked. Currently, this is too heavy. With the simple format, an agent can add a question to a `.issues` file in seconds:

```
[question] hash-fragment-security | open | Does the URL hash fragment ever leave the client in any HTTP request?
	[answer] hash-confirmed-safe | answered | Hash fragment is not included in HTTP requests per RFC 3986 -> hash-fragment-security
```

That's a complete question-answer exchange, captured as linked issues, in two lines.

### Explosion of Granularity

With the reduced overhead, agents can create issues at a much finer granularity. Instead of one issue for "build the observability pipeline," we can have 20 issues covering every sub-task, every question, every dependency, every finding. The graph gets richer. The visibility gets better. The coordination gets tighter.

## Compatibility

Both formats coexist. The same database can contain:
- Traditional JSON issues (full fidelity, complex metadata)
- `.issues` flat files (simple, agent-friendly, easy to diff)

When loaded, they merge into a single graph. An issue created in a `.issues` file can link to an issue created as a JSON file, and vice versa.

Migration is not required. Existing Issues FS databases continue to work unchanged. The `.issues` format is additive — a new way to input data, not a replacement for the existing structure.

Over time, we may find that 90% of issues are created via `.issues` files, with the traditional JSON format reserved for complex issues that need rich metadata (attachments, multi-field schemas, detailed change history). That's fine. The system supports both, and the in-memory representation is always the same full graph regardless of the on-disk format.

## Implementation Plan

### Phase 1: Parser
Build the `.issues` file parser:
- Line-per-issue format (label | status | description)
- Tab indentation for hierarchy
- Issue type prefix inference (`[bug]`, `[question]`, etc.)
- Cross-reference syntax (`-> label`)
- Integration into the Issues FS loading pipeline

### Phase 2: Check Command
Build `issues-fs check` (or `verify`):
- Parse validation (report unparseable lines)
- Consistency validation (broken refs, duplicate labels)
- Schema validation (type mismatches)
- Summary output (issue counts by type/status, link counts)

### Phase 3: Schema Management
Build `issues-fs check-schema`:
- Auto-detection of issue types and link types in use
- Predefined schemas for common types
- Schema proposal for new types
- Schema diff when data evolves beyond current schema

### Phase 4: Normalisation
Build `issues-fs normalise`:
- Convert `.issues` flat files into traditional JSON structure
- Optional — for archiving, interop, or verification
- Reversible — should produce the same in-memory graph as the original `.issues` files

### Phase 5: Agent Workflow Documentation
Write the guidance for agents:
- When to use `.issues` vs traditional JSON
- The check-before-commit workflow
- How to structure workstreams, tasks, questions in `.issues` files
- How to include Issues FS change summaries in commits
