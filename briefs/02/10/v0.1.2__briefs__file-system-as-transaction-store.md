# File System as Transaction Store: Resilience Through Persistent State

**version** v0.1.2  
**date** 10 Feb 2026  

## The Insight

Something really interesting is emerging from the way we're working. We use the file system as storage — as a database — both locally and on cloud (S3, etc.), and we have a graph-based issue tracking system with a flexible schema. We're using this to manage, track, monitor, and observe the execution flow of agentic workflows. And a powerful side effect is appearing: **the file system is becoming a transaction log**.

## Why This Matters

In normal code with normal execution flows, you have a lot of state in memory. When something crashes, that state is gone. You're left trying to figure out what happened from logs, stack traces, maybe a database that's in some half-updated state.

What I'm finding is the opposite. Because we're saving state to the file system as we go — every task, every agent delegation, every question, every issue, every response — when something crashes or fails, **the track record of where we got to is captured on disk**. The work isn't lost. The context isn't lost. You can see exactly what happened, what was done, and pick up from where it stopped.

This comes from a principle I've used for a while: **LETS — Load, Extract, Transform, Save**. The idea is that every time you do something, you save it. I used to apply this to big transformations, but I'm now applying it to small units of work. Every task delegation, every agent response, every decision point — save it.

## The Key Property: Revertability

The ability to revert changes, to have transactional processing, can only happen if you know what you actually did. That sounds obvious but it's the thing most systems get wrong.

Git commits aren't enough. Code commits tell you WHAT changed but not WHY. They don't capture the thinking, the approach that was taken, why this change occurred, the philosophy behind it. The mini issue graphs we create alongside the work capture all of that. The commit is the artifact; the graph is the reasoning.

## What We Can Capture

Pretty much everything:

- Tasks created and delegated to agents
- Agent responses and populated results
- Questions and answers mapped to tasks
- Issues created during execution
- Commands triggered, execution flows
- Every single prompt sent and received
- The decision points and why a particular path was taken
- Input/output of every transformation

In a way, we can represent the entire reality of what happened — not just the final result, but the full journey.

## Ephemeral vs Permanent

Not all of this needs to survive forever. There's a distinction:

- **Ephemeral captures** — used to monitor, track, and understand execution flows in the moment. Can be deleted or compressed once you have the consolidation. Think of it like detailed debug logging that you roll up into a summary.
- **Permanent records** — the consolidated view. Input, output, key decisions, final state. This is the business record of what happened.

The pattern is: capture everything during execution (be generous, disk is cheap and fast), then consolidate once something is completed. You keep the summary, and either archive or discard the granular trace. That's a business decision per use case, but the point is you HAVE the data to make that choice.

## The Non-Problem: Performance

This is important — the bottleneck is NOT disk access. Writing to the file system is super fast. Memory-FS makes it even faster when you're running in memory. The challenge was never "can we afford to write this?" The challenge was always "can we understand what happened? Can we recover? Can we reverse?" And persistent state on every action is what solves that.

## How This Connects to Everything Else

This pattern ties directly into several things we're already building:

- **Memory-FS abstraction** — the transaction store works whether you're in memory, on disk, in S3, wherever. Same code, same pattern, different storage.
- **Issues FS as the graph** — the issue graphs ARE the transaction log, structured and queryable. Not flat log files but connected nodes and edges with schemas.
- **The transparency model in SGraph Send** — we're already doing this for user-facing transparency (every action on a transfer is logged). This is the same pattern applied to system internals.
- **The action logging from the v0.1.0 review** — logging every REST call related to a particular id/asset. That's this pattern applied to API interactions.

## The Vision

Imagine every agentic workflow produces, as a side effect, a complete graph of what it did: every step, every decision, every input and output. That graph is stored as files (Issues FS), queryable, navigable, and can be used to:

- **Resume** — pick up exactly where a failed workflow stopped
- **Revert** — undo specific steps without losing the rest
- **Audit** — understand exactly what happened and why
- **Replay** — re-execute a workflow from any checkpoint
- **Learn** — apply LLMs to the execution graphs to improve future runs
- **Debug** — when something goes wrong, the full context is right there

And all of this is just a natural side effect of the LETS principle applied consistently: every action saves its state.

- **Architect**: design the transaction store pattern formally. What's the schema for an execution step? How does ephemeral vs permanent consolidation work? How do we handle the rollup from granular traces to summaries?
- **Dev**: start applying the LETS principle to the current agentic workflows. Every task delegation and response should write state to the file system. I'll provide code samples from existing projects.
- **QA**: this pattern makes your life easier — when tests fail, the full execution trace is on disk. Start using it. Also test the resume-from-failure scenario explicitly.
- **Historian**: execution graphs are historical records. Think about how this connects to the version journaling practice — the journal entry for a version could be derived from the consolidated execution graphs of what happened in that iteration.
- **Cartographer**: map out what data we're already capturing as files vs what we're losing to in-memory state. Identify the gaps.
