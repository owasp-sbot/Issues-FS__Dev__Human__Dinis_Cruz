## 2. Playwright Screenshots as Living Documentation

This is the key idea: use the actual screenshots from actual QA tests as the documentation.

### How it works

The QA team is already using Playwright to run tests. What I've done in the past — and it works really well — is take screenshots at key points in the test script and use those as documentation images.

Think about it: what better way to have up-to-date documentation than screenshots created by tests that represent the actual user acceptance criteria? The docs can never go stale because they're regenerated every time the tests run.

### What this looks like

Imagine a documentation page where:

1. You describe what to do: "go to this page"
2. Screenshot from the test
3. You show the Playwright code: `playwright.open(page)`
4. Next step: "click on this thing"  
5. Another screenshot
6. The Playwright code for that action

So the documentation is literally the test script presented as a walkthrough, with real screenshots inline. The code IS the explanation.

### Versioning

Each IFD (Iterative Flow Development) version should have its own base folder. When there's a new release, new base folder, new screenshots. The documentation for each version becomes the acceptance criteria for that version — it's what we proved works.

### Task for QA

Figure out the workflow: how to run the Playwright tests, how to capture screenshots at the right points, how to save them to the right folder for the website. The save is simple — just write to a particular folder that the website picks up.

## 3. Two Websites, Not One

Important distinction: the website described above is the **public-facing, official marketing and docs site**. External audience.

Separately, the journalist should have an **internal site** — more like an intranet. This is where the journalist publishes briefings about what's going on, status updates, internal analysis. Not public. Think of it as the project's internal newsletter.

The journalist contributes to BOTH — public articles for the external website, and internal briefings for the intranet.

## 5. Version Journaling

We have a gap: there's no journal of what happens at each release or major push. We need this.

Every time we do a release, every time I update the submodules, every time there's a version bump — we should be capturing what happened. Think of it like a contextual git reflog: not just what commits were made, but what was going on in the project, what decisions were taken, what changed and why.

This should be linked to versions. Everything is version-controlled, so every version should have a corresponding journal entry that provides the narrative context. When someone asks "what happened in v0.1.2?" there should be a clear answer, not a git log to sift through.

This also answers a meta-question we keep hitting: "have we already done X?" or "where is the current status of Y?" Right now there's no single place to read that. The version journal is that place.
