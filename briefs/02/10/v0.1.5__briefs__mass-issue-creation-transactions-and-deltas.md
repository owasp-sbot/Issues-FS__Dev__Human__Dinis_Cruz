# Mass Issue Creation: Transactions, Deltas, and Graph Diffs

**version** v0.1.5  
**date** 11 Feb 2026  

## The Trigger

We just had a session where Claude created a bunch of issues by editing JSON directly. It worked, but it exposed the question: what's the right way to mass-create and mass-edit issues? Editing raw JSON is fragile. We need better interfaces.

## The Ways to Communicate Changes

There are several possible approaches, and we should support multiple:

### 1. REST API
Call the API endpoints directly. Works locally and eventually remotely. Straightforward for single operations, can be batched.

### 2. Python code (as tests/transformations)
This is the one I like most. Instead of giving me JSON, give me Python code that uses the Issues FS client APIs to make changes. Code is a very reliable way to express changes, and both humans and LLMs write code effectively.

The code can:
- Import the Issues FS client
- Make changes using the proper API
- Include assertions to verify the changes worked
- Be executed as tests

### 3. Batch JSON files
A set of JSON files that describe the changes to make. A batch processor reads them and applies the changes. Simpler than code, but less expressive.

### 4. Batch command mode
Provide a list of commands/instructions that get executed in sequence. CLI-style but batched.

### The preference
If LLMs can write code effectively (and they can), then **code is the best interface**. The LLM can even clone the client locally, use it to generate and validate the JSON, and ensure the changes are correct before handing them over. Code gives you: type checking, assertions, error handling, sequencing — all for free.

## The Transaction Model

This is the important evolution. When you're making 5, 7, 20 changes to the graph, you want **transactional semantics**:

- All changes succeed, or none of them commit
- Defensive coding — check preconditions before applying changes
- Tests before AND after — verify the graph is in the expected state before starting, verify it's in the expected state after finishing
- If the issues aren't in the state you expect (because someone else updated them), don't commit

This is critical for agents. Without transactions, an agent can make a batch of changes where half succeed and half fail, leaving the graph in an inconsistent state. Or an agent can make changes based on stale assumptions — the issue it thought was "open" was already "closed" by another agent.

### The pattern:

```
1. Snapshot the current state (digital twin "before")
2. Verify preconditions — are the issues in the expected state?
3. Apply changes
4. Verify postconditions — is the result what we expected?
5. If all checks pass → commit
6. If any check fails → rollback, report what went wrong
```

This is the same LETS pattern (Load, Extract, Transform, Save) from the transaction store brief, applied to issue graph modifications.

## Graph Deltas: Before and After

I want to be able to visualise a batch of changes as a graph diff:

### What a delta shows
- **Before**: the graph state before the changes
- **After**: the graph state after the changes
- **Diff**: what was added (new nodes, new edges), what was modified (changed properties), what was removed (deleted nodes/edges)

### Why this matters

1. **Review before commit** — I can see "these are the 20 changes the agent wants to make" as a visual diff of the graph, not as a list of JSON mutations. Much easier to understand the impact.

2. **Review after commit** — between git diffs, I can see how the issue graph evolved. Not just "these files changed" but "the graph went from this shape to that shape."

3. **Agent communication** — instead of an agent saying "I want to make these changes" as a list of operations, it says "here's what the graph looks like now, and here's what it would look like after." The delta IS the proposal.

4. **Conflict detection** — if two agents propose deltas that overlap, you can see the conflict in graph terms, not just file-level merge conflicts.

### Graph delta as an issue type

A proposed set of changes (a delta) is itself an issue. It has a before-state, an after-state, a description of what's changing and why. It can be reviewed, approved, rejected, or modified. It links to the issues it affects.

This connects to the atomic branch workflow: every branch IS a delta. The branch contains the proposed changes, the graph diff shows the impact, the review approves or rejects the delta.

## How This All Connects

| Interface | Best for | Transaction support |
|-----------|----------|-------------------|
| Raw JSON edit | Quick prototyping | No — manual, error-prone |
| REST API | Single operations, integrations | Per-call, no batch |
| Python code/tests | Batch changes, agent workflows | Yes — assertions, preconditions, rollback |
| Batch JSON | Simple bulk imports | With a processor, yes |
| CLI batch mode | Scripted workflows | With sequencing, yes |

The Python code approach wins for most scenarios because it naturally supports the transaction model — assertions ARE precondition/postcondition checks, and tests ARE the verification step.

## For the Agents

- **Architect**: design the transaction model for batch changes. What does the "snapshot → verify → apply → verify → commit/rollback" workflow look like in code? What are the client API methods needed?
- **Dev**: create the Python client methods for batch operations. At minimum: `snapshot_state()`, `apply_changes(changes)`, `verify_state(expected)`, `commit()`, `rollback()`. The LLM should be able to write a self-contained Python script that makes batch changes with full transaction safety.
- **QA**: the transaction model is testable. Create scenarios: concurrent modifications, stale state, partial failures. Verify that the rollback works and the graph stays consistent.
- **Cartographer**: visualise graph deltas. Take a before-state and an after-state and show: nodes added (green), nodes removed (red), nodes modified (yellow), edges added/removed. This is the visual diff that makes batch changes reviewable.
- **Designer**: the graph delta visualisation needs UX thought. How does a reviewer navigate a large delta? Can you filter to show only additions, only removals? Can you drill into a specific changed node to see what properties changed?
