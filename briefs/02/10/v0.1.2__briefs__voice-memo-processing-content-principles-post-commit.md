# Issues FS: Voice Memo Processing, Content Principles, and Post-Commit Actions

**version** v0.1.2  
**date** 10 Feb 2026  

## 1. Voice Memo Processing Workflow

I want a workflow where I can dump a voice memo into a folder and have it processed and catalogued. This is probably a librarian role task.

### What "processed" means

From every voice memo, extract and categorise:

- **Tasks** created from it
- **Notes** captured
- **Actions** scheduled
- **Ideas** recorded (even if not actionable yet)
- **Questions** asked — and eventually, the answers to those questions

Then I want a **debrief document** for each voice memo that says: from this memo, these tasks were created, these notes were made, these actions are scheduled, these ideas are captured, here are the questions and here are the answers. Every item should be hyperlinked to the issue or action that was created from it.

This way nothing gets lost between a voice memo and actual work. And I can verify: did we cover everything I said?

This workflow should also work for other people — remember we can have multiple humans in the loop, not just me. Other agents or other people can provide input that needs the same processing.

## 3. Content Principle: Issues Are Not Master Sources of Data

This is important and I want it captured as a principle.

Although we can store markdown and large content inside issues, **issues should not become the master source of that data**. The master source should be a markdown file in the folder structure that makes sense. The issue links to it.

### The pattern

1. You might START with content in an issue — that's fine for capturing something quickly
2. But eventually that content should live in a proper `.md` file in the right location
3. The issue then contains a **file link** to the markdown file
4. The markdown file's front matter contains the issue ID / node ID / label ID — so we know the file is linked to the graph

### Why this matters

As we build things like principles, directives, roadmaps, taxonomies — these are anchors for all our decisions. They need to live as proper documents, not buried inside issue metadata. The issue graph gives you the relationships and navigation. The documents give you the content.

### File Link issue type

We probably need a link type called `file-link` or similar, which contains:

- File location / path
- Date last seen / verified
- Hash of the file content
- Hash of the commit that was used
- Repo where it exists
- Title (which should just be a representation of the file's actual title)

This lets us know when a file has changed since the issue last referenced it, and keeps the graph in sync with the actual content.

## 4. Post-Commit Actions and Graph Updates

I want us to start having post-commit actions that update the Issues FS graph automatically.

### The idea

After a commit (or more practically, after a tag — since we already have tag actions and this avoids infinite commit loops), we:

- Create an issue representing that commit/tag
- Link it to the parent release (minor commit links to major version)
- Link it back to the repo
- Capture metadata: what changed, what issues were addressed

The tag action is the natural place to do this because it's already part of our workflow and it's a discrete event (no risk of infinite commit loops).

### Why this matters

Right now, commits happen and the Issues FS graph doesn't know about them. We're missing the connection between "work was done" and "the graph reflects that work." This closes that loop.

## 5. Feature Requests for Issues FS

### Issue ID as folder name
There are cases where using the label ID as the folder name is inefficient or doesn't make sense — especially when we need guaranteed uniqueness and want to avoid conflicts. We should support using the issue ID directly as the folder name on disk.

### Change Issue ID to GUID
The issue ID should change from an Object ID to a random GUID. This is more robust for uniqueness guarantees and is also powerful for the use cases we're building toward.

## For the Agents

- **Librarian**: you own the voice memo processing workflow (Section 1) and the intake/triage queue (Section 2). Design the debrief document format. Also manage the backlog of unprocessed files and voice memos.
- **Conductor**: the roadmap (Section 2) is your responsibility to structure. Break the collected ideas into milestones, flag cross-project items for extraction.
- **Architect**: the file-link issue type (Section 3) and the content-vs-issue principle need to be formalised into the Issues FS schema. Also design the post-commit action flow (Section 4).
- **Dev**: the two feature requests (Section 5) — issue ID as folder name support, and changing issue ID to GUID. Size these and add to the backlog.
- **DevOps**: the post-commit / post-tag action that creates issues in the graph (Section 4). This hooks into the existing CI pipeline.
- **Historian**: once the post-commit issue creation is working, you'll have an automatic log of every release. Start thinking about how this feeds into the version journaling practice.
