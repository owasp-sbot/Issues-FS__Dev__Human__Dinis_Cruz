## Architecture Decisions Made During Implementation

### 1. Label Format — Non-Issue

The v0.1.7 brief uses `{Type}-{Number}` labels (e.g., `Task-1`, `Bug-3`, `User-Journey-1`) which match the existing `Safe_Str__Node_Label` regex `^[A-Z][a-zA-Z]*(-[A-Z][a-zA-Z]*)*-\d{1,5}$` exactly. No ADR, no slug field, no regex relaxation needed.

### 2. Intermediate Representation

The parser outputs `Schema__Issues_File__Line` (not `Schema__Node` directly), separating parsing from node creation. This follows the consensus from the Feb 13 debrief.

### 3. Lenient Parsing

Errors are collected and parsing continues. A file with 100 lines and 3 errors will produce 97 valid issues plus 3 error reports.

### 4. Type Inference from Labels

`Task-1` → type `task`, `User-Journey-1` → type `user-journey`. The type is the label prefix (everything before the final `-N`), lowercased, with internal hyphens preserved.

### 5. JSON Takes Precedence

When `nodes_list_all()` discovers a `Task-1` in both `data/task/Task-1/issue.json` and `workstream.issues`, the JSON version wins. `.issues` nodes only appear if no JSON node exists with the same label.

### 6. Cache with Boolean Flag (Not None)

Type_Safe enforces that once an attribute is set to a non-None value, it cannot be set back to `None`. The `.issues` node cache uses `issues_file_loaded: bool` flag instead of checking `issues_file_nodes is None`.

### 7. Predefined Schemas

7 type schemas defined: task, bug, workstream, feature, question, risk, user-journey. Each defines valid statuses. Unknown types are flagged but not treated as errors (extensibility).
