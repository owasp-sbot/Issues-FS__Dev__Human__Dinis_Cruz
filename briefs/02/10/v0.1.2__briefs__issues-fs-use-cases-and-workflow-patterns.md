# Issues FS: Use Cases & Workflow Patterns

**version** v0.1.2  
**date** 10 Feb 2026  

## Overview

This memo captures three related but distinct use cases for Issues FS, plus a broader architectural pattern that emerges from them. They all build on the same core idea: the graph-native, fractal nature of Issues FS makes it powerful well beyond just tracking issues.

---

## Use Case 1: Privacy-First GitHub Backup & Sync

The idea is a service — built on the Issues FS codebase — that provides a privacy-first, sovereignty-first backup and sync solution for GitHub data. Starting with GitHub, but could extend to others.

### How it works

A browser-based client-side solution that connects to GitHub and captures all the data elements the current user has access to that are NOT normally backed up in Git — issues, repo config, settings, metadata, all of it — and stores them in a Git-native format using Issues FS.

### The key constraint: zero-knowledge server

Two modes:

1. **Server as enabler only** — the server just provides guidance, a UI, and a way to access the data. No major service running. Data is stored either on the client or in another location the client has access to. The server never sees the data.

2. **Encrypted backup** — data is stored on the backend but encrypted, where only the client has the key. Without the client keys, the data is not accessible. The server side service never has access to the plaintext data.

This is the same security model as SGraph Send — the server never sees the data. Which means no authentication headaches, no PATs stored server-side, no credential management. The server side is inherently secure because it has nothing worth stealing.

### Why this is valuable

The backed-up data isn't just a safety net — it's also a way to access GitHub data in a much more scalable, parsed, filterable way. Want to query issues differently than GitHub's UI allows? You can, because you have the data locally in Issues FS format.

We can also run Python in the browser via Pyodide, which means the full Issues FS codebase can run client-side. No server dependency for the core functionality.

## Use Case 2: Git on Git — Digital Twin of GitHub Infrastructure

This is the "infrastructure as code, but we don't have the code of the infrastructure" problem.

Think about it: we have all these practices for controlling infrastructure via code and CI pipelines, but we have no code or data capturing the actual infrastructure changes. We can't verify that a change we made actually worked, because we have no before/after record of the configuration state. That's kind of crazy.

### The approach

For every repo (or at least every critical repo), create a sidecar repo that contains all the non-file information about the repo — configurations, settings, issues, actions, workflows, everything that isn't already in the Git commit history.

This sidecar repo, structured using Issues FS, gives you:

- A backup you can sync and store offline
- Point-in-time snapshots of configuration state
- Change control and recovery (you can see what changed and roll back)
- A digital twin of your GitHub infrastructure

You could also put this directly in the repo itself (which has some interesting implications), but the sidecar approach is cleaner.

## Use Case 3: Graph Representation of GitHub Data

This builds on the previous two. One of the powers of Issues FS is that it's graph-native — fractal, nodes and edges, relationships. GitHub data is also inherently a graph, but GitHub doesn't expose it that way.

### The problem

In multi-repo deployments with massive workflows, actions, issues across repos — all of those are nodes in a graph, but they're not connected. No visibility, no relationships, no way to easily navigate or manipulate the whole picture.

### The hypothesis

Even if all we did was replicate GitHub data and add NO extra data — just visualise and connect what's already there — this would be ridiculously valuable for organisations to understand what's happening. Management visibility, quality assessment, contribution tracking.

This becomes even more critical in the agentic world, where you'll have lots of agents interacting with repos and contributions growing exponentially. You NEED a graph view to keep things under control and understand quality.

### What this looks like

Imagine all GitHub issues, commits, configs, and structure saved as files managed by Issues FS. A markdown version of GitHub that you can navigate in folders. Every piece of content is a node, every relationship is an edge, and the content isn't hidden inside the issues database — it's right there in the folder structure.

Then we can apply LLMs on top of this, and they can do genuinely useful analysis because the data is structured, connected, and navigable.

## Pattern: Markdown as Master Data, Issues FS as the Graph

This is the broader architectural pattern that emerges from the use cases above, and I want to capture it separately because it's a different way of thinking about Issues FS.

### Traditional Issues FS usage

Issues FS is the centre of gravity. You add issues, you connect things. Issues FS is the master data store. The graph IS the data.

### The inversion

Here, **the content in Markdown files is the master data**. That's where all the information lives. What Issues FS provides is the graph OF those files — the relationships, the connections, the structure.

### How it works

- A file has an attribute with a particular value → Issues FS creates an issue type, a schema, a link type connected to that attribute
- Every file gets a "projection" created from it — its graph representation
- When you make a change to the content, the graph updates accordingly
- The user only interacts with the Markdown files — they never edit the Issues FS database directly

So it's almost like every document (and potentially every paragraph, every section) comes with its own Issues FS representation that is a projection of it. Then we create a consolidated graph across all documents, and now we can navigate, query, and understand the content through the graph.

### Why this matters

- Content is navigable and maintainable in its natural form (Markdown)
- Much more user-friendly — people edit documents, not databases
- The graph relationships are derived, not manually maintained
- Markdown already supports graph-like attributes via front matter (nodes and edges in document form)
- We can layer semantic graphs on top — graphs from the text, from sections, from structure
- LLMs can work with both the content and the graph simultaneously

The key insight: **you maintain the content, not the graph.** The graph is a derived artefact that provides structure, navigation, and queryability on top of human-maintained documents.

## For the Agents

- **Architect**: these three use cases share a common infrastructure need — client-side Issues FS execution (Pyodide), zero-knowledge server patterns, and the markdown-as-master-data projection model. Design these as shared capabilities, not one-off implementations.
- **Dev**: Use Case 1 (GitHub backup) is probably the first to build since it exercises the core pattern. Start with the client-side Issues FS + GitHub API integration.
- **AppSec**: the zero-knowledge model here mirrors SGraph Send. Review how the encrypted backup mode would work — key management, what the server can and can't see, attack surface.
- **Cartographer**: the graph representation of GitHub data (Use Case 3) is directly your territory. Start mapping what GitHub data looks like as an Issues FS graph — what are the node types, edge types, and how do multi-repo relationships connect.
- **Librarian**: the markdown-as-master-data pattern has implications for how we organise docs across all projects. Think about how this pattern could apply to our own documentation.
