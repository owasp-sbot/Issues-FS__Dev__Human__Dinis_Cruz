# Not All Code Changes Are the Same: Blast Radius and the Authorization Model for Code

**version** v0.1.5  
**date** 11 Feb 2026  

## The Problem

Not all code changes are the same. But we treat them as if they are. A one-line CSS tweak and a refactor of a core authentication function go through the same process, with the same visibility, and the same (lack of) blast radius analysis.

This has always been a problem. But it's getting dramatically worse with LLM-assisted development, for two reasons:

1. **Speed** — we're coding faster, making more changes, shipping more frequently. More changes = more opportunities for unintended side effects.
2. **Context gap** — we don't provide LLMs (or developers) with enough context about what the code does, what it connects to, what the blast radius of a change is. Even if the LLM were perfect, it would still make mistakes if it can't see the blast radius.

This isn't just a vibe coding problem. Experienced developers doing serious LLM-assisted development hit this too. The velocity amplifies the risk.

## The Root Cause: Code Has No Authorization Model

Think about how we architect code. It's essentially a **flat authorization model** — everything runs as admin. Any code can call any other code. Any function can modify any state. The only boundaries are the files and modules you happen to be working in, and that's far too much scope.

We do have some natural boundaries — libraries and abstraction layers that control damage by encapsulating core dependencies. But that's accidental architecture, not deliberate blast radius management. Nobody designs their codebase by asking "what should this code be ALLOWED to change?"

Compare this to infrastructure: we have IAM policies, least privilege, network segmentation, blast radius containment. We think carefully about what each component can access and affect. But for application code? Everything is root. Every change can touch everything.

## Why Bugs Happen

Most bugs aren't created because someone wanted to create a bug. They're created because someone **didn't understand the side effects** of their change. They changed function A, not realising it was called by workflow B, which feeds into feature C, which has a non-functional requirement for reliability that just got broken.

And this usually only manifests in production, because that's where you're exposed to the much bigger variety of data and use cases that exercise the code paths you didn't know you were touching.

## The Solution: Semantic Code Graphs

We need to **map out what the code is doing** — not just structurally (what calls what) but semantically (what does this code MEAN in business terms).

This requires connecting multiple layers:

- **Code graph** — functions, classes, modules, dependencies, call chains
- **User stories and features** — what business capability does this code support?
- **Non-functional requirements** — security, reliability, performance, compliance
- **Data flows** — what data does this code touch, transform, expose?

When you connect these layers, a code change stops being "I changed line 47 in utils.py" and becomes "I changed the function that validates user input for the payment flow, which has a reliability SLA and a PCI compliance requirement." Now you know the blast radius. Now you know what tests to run. Now you know who needs to review it.

## Type_Safe as a Defence Layer

This is exactly why the Type_Safe approach in our Python development provides so much resilience. The framework enforces:

- **Runtime type validation** — not just at compile time, at execution time
- **Schema-driven design** — every data structure has a schema with validations
- **No raw primitives** — no bare `str`, `int`, `float`, or collections anywhere in the code. Every value is a domain-specific class: `Positive_Number`, `Age`, `Network_Port`, `Username`, `Email`, `URL_Query`, etc.
- Each domain type contains its own **validation logic** — a `Network_Port` knows it must be 1-65535, an `Email` knows its format, a `URL_Query` knows what characters are allowed

What this gives you: by the time data enters the system, it's already well-formed and in a good state. You've eliminated entire categories of bugs at the boundary. The blast radius of a change to a domain type is visible — you can see every function that uses `Email` and know they're all affected.

This is a concrete implementation of the "authorization model for code" idea — the type system constrains what's possible. You can't accidentally pass a raw string where an Email is expected. The type boundary is a blast radius boundary.

## The Change Classification We Need

If not all code changes are the same, we need a way to classify them. Rough categories:

- **Cosmetic** — UI text, CSS, formatting. Near-zero blast radius.
- **Additive** — new feature, new endpoint, new function. Contained blast radius if well-designed.
- **Modificative** — changing existing behaviour. Blast radius depends on what calls it.
- **Structural** — refactoring, moving code, changing interfaces. Potentially wide blast radius.
- **Core** — changing fundamental primitives, base classes, shared utilities. Maximum blast radius.
- **Security-sensitive** — authentication, authorization, encryption, data handling. Blast radius includes compliance implications.

Each category should trigger a different level of review, different tests, and different visibility requirements.

## How Issues FS Supports This

This brief is a companion to the code quality culture brief — together they describe why blast radius visibility matters and how Issues FS provides the infrastructure for it.

### Code structures as issue types

Represent functions, classes, modules, and endpoints as nodes in the Issues FS graph. Dependencies between them are edges. Now blast radius is a graph traversal: change this node → follow edges → see everything affected.

### Change classification in the graph

When a code change is committed, classify it (cosmetic, additive, modificative, structural, core, security-sensitive) and store that classification as metadata on the issue. The classification drives what review process kicks in.

### Type_Safe types as graph nodes

Every Type_Safe domain type (`Email`, `Network_Port`, `Username`, etc.) becomes a node. Every function that uses that type is linked by an edge. Change the type → traverse the graph → see the blast radius across the entire codebase. This is the authorization model made visible.

### Non-functional requirements as connected nodes

Security requirements, reliability SLAs, compliance obligations — all represented as nodes in the graph, linked to the code that implements them. A code change that touches a function linked to a PCI requirement automatically surfaces that compliance connection in the review.

### The velocity safety net

As LLM-assisted development increases velocity, the graph becomes the safety net. You can move fast because the blast radius is always visible. Speed without visibility is recklessness. Speed WITH visibility is just... speed.

## For the Agents

- **Architect**: design the change classification taxonomy. What are the categories? What review process does each trigger? How does this integrate with the atomic branch workflow?
- **Dev**: start tagging commits with change classification. Even manually at first — we'll automate detection later. The habit matters more than the tooling right now.
- **AppSec**: the security-sensitive classification is your domain. Define what makes a change security-sensitive and what additional review it requires. Also: the Type_Safe boundary types are security controls — document them as such.
- **QA**: different change classifications should trigger different test strategies. Cosmetic → visual regression tests. Core → full test suite. Define the mapping.
- **Cartographer**: visualise a real code change with its blast radius across all layers — code, features, non-functional requirements. Make the "not all changes are the same" argument visible.
