# Multi-Persona Message Translation: From CISO to Boardroom

**version** v0.1.2  
**date** 10 Feb 2026  

## The Concept

Building on the text-to-text graph work we've been doing — where even text is a graph that we can translate and map — I want to expand this into a scenario where the same message gets translated through multiple personas and you can SEE the connections between them.

The use case: a CISO needs to communicate to a board. But "the board" isn't one person. It's three, four, five people with completely different roles, agendas, languages, cultures, cybersecurity understanding, and priorities. There is no single message that works for all of them. So what do you actually do?

## The Four Layers

### Layer 1: Raw Data
The underlying facts, evidence, metrics, incidents — the raw material that exists. This is the ground truth. Not a message, just data.

### Layer 2: CISO's Global Message
The CISO synthesises the raw data into their message — what they want to communicate, what they're asking for, what the situation is. This is one message, one intent.

### Layer 3: Per-Board-Member Translation
The global message translated into the language, framing, and context of each individual board member. Still reflects the original intent, but now shaped by:

- The board member's **role** (CFO, CEO, COO, etc.)
- Their **persona** — personality, communication style, attention span
- Their **language and culture** — how they think about problems
- Their **cybersecurity understanding** — technical depth they can handle
- Their **agenda** — what they care about, what they're trying to achieve
- Their **current position** — constraints they're operating under

### Layer 4: What the Board Member Actually Understands
This is the critical layer. Not what we said, not what we translated, but what actually landed. The board member filters everything through their own lens.

## Why This Is Interesting

### The CFO example
A CFO who knows there's no budget will always say no. Doesn't matter what you say. So the interesting questions become:

- Is there ANY framing of this request that would get a yes? If so, what is it?
- Or can we predict in advance that this is a dead end given the current ask?
- Can we improve the original request to make it viable for this person?
- What does the CFO actually want to hear? Numbers. Bottom line. Return on investment. So frame it that way.

### The CEO example
The CEO probably wants alignment with the corporate risk register, alignment with strategic direction, brand implications. Completely different framing from the CFO, same underlying message.

### The COO example
Operations cares about disruption, uptime, process impact, resource requirements. Again, same message, completely different translation.

## The Visualisation

I'm visualising something where you can see:

- The global message on one side, the three (or more) board members on the other
- The intermediate translations in between
- **Word-to-word connections** — which words in the original map to which words in the translation
- **Meaning-to-meaning connections** — because we have the intermediate semantic graph representations, we can connect at the concept level, not just the text level
- Where raw data from Layer 1 feeds back into specific translations — because certain raw data is relevant to specific board members (the CEO needs the risk register alignment data, the CFO needs the financial impact data)

You should be able to see, at a glance, how effectively the same message communicates to three different people. And where it breaks down.

## How This Maps to Issues FS and Semantic Graphs

This is exactly what our text-to-graph work enables:

- Each layer is a set of nodes (words, phrases, concepts, meanings)
- Translations between layers are edges connecting nodes across layers
- Each board member persona is a graph of attributes (role, agenda, understanding level, etc.) that acts as a filter/transformer
- The rich intermediate representations we create during text-to-graph translation give us the semantic layer to connect meaning-to-meaning, not just text-to-text
- The whole thing IS an Issues FS graph — personas are issue types, translations are link types, the content lives in the nodes

## The Broader Pattern

This isn't just about board communication. It's a general pattern: **one message, multiple audiences, persona-aware translation, with semantic graph connections between all the representations**. Could apply to:

- Security advisories translated for different technical levels
- Product announcements translated for different stakeholders
- Incident communications across different audiences
- Any situation where the same information needs to reach different people differently

## The Prediction Angle

The really powerful thing: if you have the persona graph (what this person cares about, their constraints, their agenda) and the semantic graph of the message, you can potentially **predict the response before sending**. Will the CFO say yes or no? Is there a path to yes? What would need to change in the request? This is where LLMs on top of the graph structure become genuinely useful — not generating the message, but simulating the reception.
