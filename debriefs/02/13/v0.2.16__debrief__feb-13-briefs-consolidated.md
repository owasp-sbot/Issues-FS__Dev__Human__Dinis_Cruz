## Executive Summary

Three roles responded to the Feb 13 briefs: **Architect**, **Dev**, and **Librarian**. An additional **Explorer** deep-dive mapped the Issues-FS core module architecture. All three roles independently confirm that the `.issues` flat file parser is **feasible and well-scoped for implementation**. The single blocking question is the **label format mismatch** between the brief's proposed labels (lowercase slugs like `enable-cloudfront-logs`) and the existing `Safe_Str__Node_Label` regex (which requires `Word-N` format like `Task-42`).

**MVP Readiness Assessment: YES, with one prerequisite ADR.**

The team has sufficient knowledge of the codebase, data model, storage layer, and loading pipeline to build the `.issues` parser. The Explorer confirmed the full architecture. The Architect designed the integration points. The Dev produced a complete implementation plan with class signatures, test strategy, and scope estimate. The Librarian catalogued the briefs, identified all cross-references, and proposed the folder structure for the brief/debrief workflow.

## Role Responses

### Architect Response

**Document:** `roles/Issues-FS__Dev__Role__Architect/docs/responses/v0.2.16__response__simplified-agent-format.md`
**Branch:** `claude/respond-to-briefs-QaKVH`

**Key findings:**

1. **Feasibility: YES.** The brief proposes a second on-disk format that compiles to the existing in-memory graph. This respects the existing Memory-FS abstraction and is architecturally sound.

2. **Parser placement:** A new `issues_fs/issues/loading/` package, parallel to the existing JSON loader, producing `Schema__Node` instances that feed into the same `MGraph__Issues__Domain` graph.

3. **The Label Problem (Critical).** The existing `Safe_Str__Node_Label` regex (`^[A-Z][a-zA-Z]*(-[A-Z][a-zA-Z]*)*-\d{1,5}$`) does not accept the brief's proposed labels. Three options evaluated:
   - **Option A:** Relax the regex (weakens a fundamental type contract)
   - **Option B:** Add a `slug` field to `Schema__Node` (Architect's recommendation)
   - **Option C:** Two-pass label mapping (complex, loses diff advantage)

4. **Recommended phasing:** ADR first, then Parser (pure text), then Loader (graph integration), then Schema management, then Normalise command, then Agent workflow docs.

5. **API design:** Intermediate representation (`Schema__Parsed__Issue`) between raw text and `Schema__Node`, preserving source location for error reporting. Parser is a pure function with no side effects.

6. **Risks flagged:** Cross-file reference resolution, idempotent reload (what happens when the same `.issues` file is loaded twice), and pipe characters in descriptions.

### Explorer Findings (Core Module Assessment)

The Explorer deep-dived `modules/Issues-FS/` to map the full architecture:

- **87 Python source files** across schemas, services, storage, and graph layers
- **4-layer model:** Schema -> Domain -> Service -> Repository
- **Storage backends:** Memory (tests), Local Disk (dev), SQLite (embedded), ZIP (export) -- all behind `Storage_FS` interface
- **On-disk structure:** `.issues/config/`, `.issues/data/{type}/{label}/issue.json`
- **Node model:** 14-field `Schema__Node` with Type_Safe primitives
- **Link model:** Bidirectional with verb/inverse_verb, type constraints
- **5 default node types:** git-repo, bug, task, feature, person
- **6 default link types:** blocks, has-task, assigned-to, depends-on, relates-to, contains
- **Key finding for parser integration:** `.issues` is already in `Graph__Repository.SKIP_LABELS`, so `.issues` files won't interfere with the existing JSON scanner. The parser slots in as a parallel loading path at the Repository layer.

## Consensus Points (All Roles Agree)

1. The `.issues` flat file format is **feasible** and aligns with the existing architecture.
2. The parser should be a **new component within Issues-FS core**, not a separate repo.
3. The parser should output an **intermediate representation** (not `Schema__Node` directly) to separate parsing from node creation.
4. The **label format mismatch** is the single most important design decision and needs an ADR before the node factory can be built.
5. Phase 1 (parser only) can proceed **in parallel** with the label ADR -- the parser operates on raw strings, not `Safe_Str__Node_Label`.
6. The parser should be **lenient** (collect errors, continue parsing) not strict (fail on first error).
7. Comments (`#` lines) and blank lines should be supported even though the brief doesn't mention them.
8. The `check` command (`issues-fs check`) is the right validation interface.
