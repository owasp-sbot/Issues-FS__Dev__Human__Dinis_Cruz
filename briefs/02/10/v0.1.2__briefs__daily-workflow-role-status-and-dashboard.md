# Daily Workflow, Role Status, and the Dashboard Problem

**version** v0.1.2  
**date** 10 Feb 2026  

## Who Do I Talk To?

Meta question first: when I have a question, who do I ask?

My instinct says the **librarian**, not the conductor. Here's why: because the librarian is running on an LLM, we get an interesting best-of-both-worlds situation. We have a librarian that knows how to find things and catalogue them (the traditional librarian role), but we ALSO have a librarian that understands the language of every other role — security, architecture, development, operations, all of it. In the real world, librarians don't usually have that. Ours does.

So the librarian becomes the first point of contact for questions. They either answer directly (if it's about finding information) or route to the right role (if it needs specialist input).

## The Daily Workflow

Every morning, the first question is: **what's the status of what's going on?**

This means running a query to every role and getting a report:

- Tasks currently being worked on
- Tasks that are blocked (and what's blocking them)
- Next steps
- Questions they have for me
- Current state of affairs in that role

### How this should actually work

Here's the important thing: the answer to "what's your status?" should NOT be an agent generating new material on the spot. The agent should have been **maintaining its own issue database all along** — updating tasks, processing new information, keeping its status current. So when I ask, it's just a case of reading the current state from the issues database.

This means we need:

- A **common status structure** across all roles — similar project structure, similar schemas, similar places to look for status information. The taxonomy and ontology of status should be shared.
- The status for any role should be **navigable** — I should be able to go to a specific place in the issues database and see the status, not have an agent summarise it for me from scratch every time.

## The Feature Request: Status Dashboard UI

So now I'm asking for a new feature — a UI that shows me the current state of affairs across all roles and projects. And this triggers the meta question: what's the workflow for adding a new feature? What's the sequence of events, the tasks, the questions and answers we need to trigger?

### What this UI needs to do

With a small number of queries, show me:

- Status across all roles
- Status across all projects
- Blocked items and blockers
- Questions waiting for me
- What's coming next

### The UI-of-UIs problem

This is fundamentally a **UI of UIs**. We already have a UI that shows an individual issues database. But this is a level up — it needs to consume data from multiple issues databases across multiple projects. It's a dashboard that aggregates.

### Where does it live?

Two options, and we should have a conversation about this:

1. **New project** — an "issues dashboard" or similar, purpose-built for cross-project visibility
2. **Mode of the existing UI** — depending on how it's configured and where it runs, the current UI could have access to sub-issues databases and present a different view

I'm leaning toward option 2 if we can make it work, because it's less infrastructure to maintain. But it depends on how cleanly we can do the recursive consumption.

---

## Feature Request: Recursive Issues Folder Consumption

This is the underlying capability that the dashboard needs.

Right now, in this project, we have a situation where there are multiple projects side by side, each with their own issues folders nested inside. We need the ability — from the CLI and from the UI — to **consume recursive issues folders**. Walk the tree, find all the issues databases, aggregate them.

Without this, we can't build the dashboard. With it, the dashboard is just a view layer on top of the recursive query.

## For the Agents

- **Librarian**: you're now officially the first point of contact for questions. Think about how you triage and route — what do you answer directly vs what goes to another role? Also: the common status schema across roles is something you should propose, since you need to be able to read and summarise all of them.
- **Architect**: design the recursive issues folder consumption feature. How does the CLI discover and aggregate nested issues databases? How does the UI consume the aggregated data? Also weigh in on whether the dashboard is a new project or a mode of the existing UI.
- **Dev**: the recursive consumption feature is the blocker for everything else here. Prioritise it.
- **QA**: once we have a common status schema, create a test that verifies every role is maintaining its status in the expected format and location.
- **Conductor**: the daily status workflow needs to be formalised. Define the cadence and the expected outputs from each role. Make sure every role knows they're expected to keep their issues database current, not generate status reports on demand.
