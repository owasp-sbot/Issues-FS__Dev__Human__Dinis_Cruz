# Issues FS: Status Mapping, Personas, and Development Discipline

**version** v0.1.2  
**date** 10 Feb 2026  

## Context

This covers a batch of related ideas about understanding where we are with Issues FS, how we prove it works, and how we make sure every piece of work is driven by real needs.

---

## 1. Map the Current Status — Historian Archaeology

One of the most important things right now is understanding what we actually have. What are the real use cases that are already working? Not theoretical — for real.

We already have Issues FS being used for:

- Issue tracking
- Managing projects
- Defining intelligence and taxonomies
- Creating releases and user stories
- Coordinating agents through Issues FS
- Capturing bugs and guidance from the project itself

**Task for Historian**: go on an archaeology journey. Read every single issue that has been created across the project. Map out the different types of issues we have. Start creating the narrative of what we've built, what's been done, what patterns have emerged. Go back in time and figure out the full picture.

This connects to a point I made in another memo — we need a way to understand the work that has been done. The historian's output here should be a comprehensive map of issue types, use cases in practice, and the evolution of how we've used Issues FS.

## 2. Caching, Hashing, and Index Files

Here's the efficiency problem: if I ask the historian or journalist to give me a view of all the issues, it's incredibly inefficient to read every file every time. We need to think about caching and indexing.

The core idea: if a role has completed an analysis of a folder, and we have the hash of the folder/commit/content that was analysed, we should NOT have to read the files again. We know nothing has changed.

What I want us to explore:

- **Hash-based cache invalidation** — if the content hash matches, the previous analysis is still valid
- **Index files** — for example, a file that contains all the front matter for every file in a particular folder. One read instead of N reads.
- **M-Graph database integration** — this is coming and will help a lot, but we can start thinking about lightweight index files now
- **Projection caches** — when we create a graph projection of content (as described in the markdown-as-master-data pattern), cache that projection keyed by content hash

This is going to be essential as the data grows. We can't have every agent re-reading everything on every task.

## 3. Real-World Use Case Documentation

On the website (covered in a separate memo), we should have a section documenting use cases with real-world examples. Not theoretical "you could use it for..." but "here's how we actually used it for X, and here's what happened."

Also: a feedback/feature request mechanism. Could be user feedback, could be bot/agent feedback — "here's what I needed and couldn't do" or "here's what was hard." This feeds directly into prioritisation.

---

## 4. Development Discipline

Starting now, every piece of dev work must be driven by one of two things:

1. **Refactoring / code quality** — making what exists better
2. **Use-case-driven features** — a user (or persona) has a specific requirement and need

No more features built in a vacuum. Every feature is driven by a user need, and that need is documented.

### The testing rule

Every bug, every feature that's not yet working, should have an equivalent integration test. That test should currently fail (because the feature doesn't exist or the bug isn't fixed). When the work is done, the test passes. The bug IS a feature — its test should be right there alongside the feature tests.

As we improve our integration and unit test coverage, the test suite becomes the living documentation of what works and what doesn't.

## 5. Personas

I want us to create a set of personas that represent our user types. Not vague marketing personas — specific, named, with personality, tasks, and roles.

### What a persona looks like

- A name and personality
- A role (e.g. project manager using Jira today, open source maintainer using GitHub, security analyst, etc.)
- Specific tasks they need to do
- Their current tools and workflows
- Their pain points

### How we use them

1. **QA simulates the persona** — walks through the workflows as that persona would, implements their tasks, exercises the system from their perspective
2. **Journalist interviews the persona** — an LLM acts as the persona and gives feedback. What worked well? What didn't? What was easy? What was hard? What's objective? What's not? Could even do an NPS score.
3. **Calibration against real users** — this is the powerful part. Once we have real humans using the system, we identify which persona they map to, get their actual feedback, and calibrate: were our simulated persona answers too aggressive? Too positive? Too negative? Realistic enough? Are we missing the mark?

This gives us a statistical analysis of how well our personas predict real user experience. And the same feedback infrastructure we built for simulated personas works directly for real users.

---

## 6. Brief → Task Traceability

Every brief (including this one) should be connected to every single task and action that gets captured from it. So we can verify nothing was lost, and we can trace any piece of work back to the brief that originated it.

This is an Issues FS linking problem — the brief is a node, every task extracted from it is a node, and they're connected. When someone asks "did we cover everything from that memo?", the graph gives you the answer.

## For the Agents

- **QA**: start defining the persona set (Section 5). Think about who our users actually are and will be. Also start mapping the test-per-feature discipline (Section 4) to our current test suite — what's missing?
- **Journalist**: once QA has the personas, your job is the interviews. Also start documenting the real-world use cases (Section 3) based on what the historian finds.
- **Architect**: the caching/hashing/indexing problem (Section 2) needs a design. How do index files work? What's the schema? How does it interact with Memory-FS and eventually M-Graph?
- **Conductor**: the brief-to-task traceability (Section 6) is your responsibility. Every task that comes out of this memo (and every other memo) needs to be linked back. Set up the pattern now.
- **Dev**: the development discipline (Section 4) applies immediately. Every PR from now on should reference either a refactoring goal or a use-case-driven requirement. No orphan features.
